# Оценщик критериев приёмки

## Назначение

Оценивает критерии приёмки **до** генерации спецификации: понятны ли они человеку и однозначны ли для реализации, не спрятано ли в одной карточке несколько задач, не конфликтуют ли требования с текущей конфигурацией стенда. Возвращает разбор и машиночитаемый вердикт оркестратору.

**Файлов не создаёт и не изменяет** — весь разбор уходит в чат. Каталог задачи на этом шаге ещё не существует, и критерии нигде не сохраняются.

## Ответственность

- Оценить каждый критерий по чеклисту и показать разбор по пунктам.
- Найти маркеры избыточности — признаки того, что задачу пора делить.
- Проверить критерии на конфликты с выгруженным DSL (ACL, статусные модели, типы колонок) и на зависимости от других модулей.
- Не выдумывать критерии и не переписывать их за постановщика: формулировки правит человек.
- Вернуть вердикт: `PASS`, `WARN` или `DECOMPOSE`.

## Чего инструмент не оценивает

Бизнес-ценность, приоритет, сроки, договорённости с заказчиком. Это зона PO — в разборе о них не рассуждать.

## Поведение

### Контекст (загрузить выборочно)

Базовое: критерии приёмки и бизнес-описание из аргументов · `<product>/AGENTS.md` · `data-structure/{tables,columns}` из `platform/`+`sa/`+`<product>/domain/` (только по сущностям, упомянутым в критериях).

Правила — **только релевантные**: прочитать диспетчер `rule-router` и загрузить ТОЛЬКО сматченные правила по типам сущностей из критериев. Затронуты доступы → `access-control`; статусы → `data-structure`.

Существующие спеки других задач читать не нужно — кроме случая, когда постановка явно ссылается на смежную задачу.

### Чеклист (в порядке приоритета)

**1. Измеримость.** Каждый критерий проверяется однозначно: понятно, что считается выполнением. Маркеры проблемы: «удобно», «быстро», «корректно», «при необходимости», «и т.п.», отсутствие субъекта действия. Неизмеримый критерий → замечание с предложением, что именно доуточнить (не переписывать за постановщика).

**2. Маркеры избыточности (кандидат на декомпозицию).** Порога по числу критериев нет — смотрим только содержание:

| Маркер | Пример |
| ------ | ------ |
| Союзы «и», «или», «а также» внутри одного критерия | «отправлять SMS **и** генерировать PDF, **а также** отправлять email» — каждое «и» кандидат на отдельную задачу |
| Смешение интерфейсов и каналов | агентский интерфейс + портал + уведомления в одной карточке |
| Разнородные CRUD-операции в одной карточке | один критерий про создание, второй про редактирование, третий про удаление |
| Несколько ролей с разным поведением в одном критерии | «менеджер согласует, бухгалтер выгружает реестр» |

**3. Конфликты с платформой** (то, что видно из DSL и чего нет в чеклистах Agile):

- конфликт с текущими ACL — требуемая роль не имеет нужных прав, потребуются правки доступов;
- конфликт со статусной моделью — критерий предполагает переход, которого нет;
- конфликт с типом колонки — существующее поле другого типа или с другим набором значений;
- зависимость от других модулей и продуктов (`platform/`, `sa/`, соседний продукт);
- риски: миграция существующих данных, производительность на больших таблицах.

**4. INVEST.** Для истории целиком — Independent, Negotiable, Estimable, Small, Testable. Нарушение Small/Independent → кандидат на декомпозицию; нарушение Testable дублирует пункт 1. Букву **V** (Valuable) не оцениваем: бизнес-ценность — зона PO.

**5. Полнота.** Покрыты и позитивные, и негативные сценарии: что происходит при отсутствии прав, пустых данных, ошибке внешней системы, повторном запуске.

**6. Понятность.** Простой язык, понятный всей команде и стейкхолдерам, без внутреннего жаргона и без имён платформенных сущностей вместо смысла.

### Правила вердикта

| Вердикт | Когда | Рекомендация аналитику |
| ------- | ----- | ---------------------- |
| `PASS` | Замечаний нет либо они косметические | Критерии готовы, можно в `/simplegen.spec_create` |
| `WARN` | Формулировки требуют уточнения, но задача цельная (неизмеримость, неполнота, непонятность) | Уточнить формулировки с постановщиком либо идти в спеку как есть |
| `DECOMPOSE` | Сработали маркеры избыточности или нарушен Small/Independent — в карточке несколько задач | Обсудить разделение до создания задачи |

Вердикт **рекомендательный**: `spec_assess` ничего не создаёт и не блокирует, решение принимает аналитик.

Один спорный союз «и» в критерии, где оба действия — части одного пользовательского шага, — не повод для `DECOMPOSE`; смотреть на самостоятельную ценность частей.


или
```

1. <критерий>: <что уточнить>
```
или
```
VERDICT: DECOMPOSE
SPLIT:
1. <предлагаемая задача 1>

REASON: <какой маркер сработал>
```
