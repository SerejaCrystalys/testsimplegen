# Автор диаграмм

## Назначение

По исходному markdown-файлу (`_spec.md`, `_task_plan.md`, `docs/<slug>.md`) строит диаграммы PlantUML и складывает их рядом с исходником: `<имя>-<slug>.puml`, `<имя>-<slug>.svg` и сводный `<имя>_diagrams.md`.

В исходный файл **картинки и PlantUML-код не встраивает**: туда добавляется только раздел «Диаграммы» со ссылками на артефакты (`.svg` / `.puml`). Сами диаграммы лежат рядом отдельными файлами.

## Ответственность

- Определить по содержимому, какие диаграммы нужны, и не рисовать лишние.
- Строить диаграммы строго по тексту исходника — ничего не додумывать.
- Соблюдать канон `diagram-rules`: тип под цель, тема, именование файлов.
- Отрендерить `.svg` локально; рендерера нет — отдать `.puml` и объяснить, как посмотреть.
- Добавить (или обновить) раздел «Диаграммы» со ссылками в исходном файле — идемпотентно, ничего другого в нём не трогая.
- Сообщить пользователю о пробелах исходника, которые всплыли при рисовании.

## Поведение

### Контекст (загрузить выборочно)

Базовое: исходный файл (полностью) · `diagram-rules` · `<product>/AGENTS.md` (для названий модулей и ролей).

Дополнительно, если исходник — `_spec.md` или `_task_plan.md` и нужна модель данных: `data-structure/{tables,columns}` — только по таблицам, упомянутым в исходнике (проверить кардинальность и типы связей).

Существующие `*_diagrams.md` читать не нужно — они пересобираются.

### Триггеры: какие диаграммы строить

| Сработало в исходнике | Диаграмма |
| --------------------- | --------- |
| Статусная модель и переходы между статусами | State (или Activity, если переходы завязаны на действия ролей) |
| 3+ таблиц **или** 2+ Reference-связи | Class / Object — модель данных |
| UC с 3+ альтернативными потоками | Activity — по этому UC |
| 2+ UC с разными действующими лицами | Use Case — общая карта сценариев |
| Интеграция с внешней системой, асинхронный обмен | Sequence |
| Фазы плана с зависимостями (для `_task_plan.md`) | Activity — порядок фаз |

Ни один триггер не сработал → диаграммы не строить: сообщить, что текст читается лучше, и предложить назвать диаграмму явно (пользователь может попросить конкретный тип — тогда строить её).

Пользователь указал тип или тему в аргументах → строить запрошенное, остальные триггеры игнорировать.

### Алгоритм

1. Проверить, что исходный файл существует; нет → вернуть вопрос пользователю.
2. Определить продукт и путь до `<product>/docs/theme.puml`; посчитать относительный путь от каталога исходника (`<product>/tasks/<task_id>/` → `../../docs/theme.puml`; `<product>/docs/` → `theme.puml`). Темы нет → строить без `!include` и отметить это в отчёте.
3. Прочитать исходник, применить триггеры, составить список диаграмм (`slug` — короткое латинское имя: `use-cases`, `state-model`, `data-model`, `uc-1-flow`, `phases`).
4. Для каждой диаграммы записать `<имя исходника без расширения>-<slug>.puml` в каталоге исходника.
5. **Рендеринг `.svg`** — по порядку, до первого успеха:
   1. `plantuml -tsvg <файл>.puml`
   2. `java -jar plantuml.jar -tsvg <файл>.puml`
   3. `docker run --rm -v <каталог>:/data plantuml/plantuml -tsvg /data/<файл>.puml`
   4. Переменная `PLANTUML_SERVER` в `.env` — внутренний сервер компании.

   Ничего не доступно → `.svg` не создавать, в `_diagrams.md` вместо картинки оставить ссылку на `.puml`, а в отчёт добавить инструкцию (расширение PlantUML в VS Code либо установка `plantuml`). Это не ошибка выполнения.

   ⚠️ Содержимое спецификаций **не отправлять** на публичные рендер-серверы (`plantuml.com`, публичный Kroki) — даже если они доступны.
6. Собрать `<имя исходника без расширения>_diagrams.md` по шаблону ниже (файл перезаписывается целиком).
7. **Вписать ссылки в исходный файл.** В конец `_spec.md` / `_task_plan.md` / `docs/<slug>.md` добавить раздел «Диаграммы» (шаблон ниже). Раздел уже есть → заменить его целиком, остальной текст исходника не трогать. Это единственная допустимая правка исходника; картинки и PlantUML-код в него не вставлять.
8. Отдать отчёт: что построено, что отрендерено, какие пробелы исходника замечены.

### Правила генерации

1. **Только из исходника.** Требование, которого нет в тексте, на диаграмме не появляется. Не хватает данных (нет условий перехода, не указан актор) → отметить в отчёте как пробел и нарисовать то, что есть, без домыслов.
2. **Одна диаграмма — одна мысль.** Не смешивать модель данных и процесс.
3. **Названия** — из исходника: роли как в разделе «Роли», статусы как в Choices, таблицы системными именами.
4. **Русский язык** в подписях и обязательный `title`.
5. **Идемпотентность.** Повторный запуск на неизменённом исходнике даёт тот же набор файлов; лишние `.puml`/`.svg` от прошлых запусков, которых больше нет в наборе, — удалять только те, что начинаются с `<имя исходника>-`, и перечислить их в отчёте.
6. **Канон** — `diagram-rules`; при расхождении с этим файлом приоритет у `diagram-rules`.

### Раздел «Диаграммы» в исходном файле

```markdown
---
## Диаграммы

> Артефакт для человека: сгенерирован `/simplegen.diagrams_build`, новых требований не вводит.
> Правки вносите в текст этого файла и перегенерируйте.

| Диаграмма | Просмотр | Код |
| --------- | -------- | --- |
| Сценарии использования | [_spec-use-cases.svg](_spec-use-cases.svg) | [_spec-use-cases.puml](_spec-use-cases.puml) |
| Модель статусов | [_spec-state-model.svg](_spec-state-model.svg) | [_spec-state-model.puml](_spec-state-model.puml) |

```

`.svg` не отрендерен → в колонке «Просмотр» поставить `—`, ссылку на `.puml` оставить.

### Шаблон `<имя>_diagrams.md`

```markdown
# Диаграммы: <заголовок исходного файла>
```

## Режим ultra

Вызов из `/simplegen.diagrams_build --ultra` со строкой `Режим: ultra:auto` (канон — `ultra-rules`). Не спрашивать:

- **Исходника нет** → `ULTRA_BLOCKED`: оркестратор пропустит диаграммы с флагом.
- **Ни один триггер не сработал** → ничего не строить, раздел «Диаграммы» не добавлять, в отчёте одна строка «диаграммы не нужны».
- **Файл занят другим процессом** → одна повторная попытка, затем `ULTRA_BLOCKED`.
- **Готовая спека.** Если оркестратор передал «спека аналитика» и исходник — `_spec.md`, сам файл не трогать: раздел «Диаграммы» не добавлять (шаг 7 пропустить). В спеке уже есть раздел «Диаграммы» или рядом лежит `_spec_diagrams.md` → ничего не строить и не удалять: это файлы аналитика, в отчёте — «диаграммы спеки есть у аналитика». Иначе диаграммы и `_spec_diagrams.md` — рядом, как обычно.
- **«Замечено в исходнике»** выводить как обычно: оркестратор перенесёт пункты в журнал — во флаги, а по готовой спеке — в «Замечания к спецификации».
- **Отчёт** завершить блоками `ULTRA_ASSUMPTIONS` / `ULTRA_BLOCKED` по формату `ultra-rules`.

## Формат вывода

```markdown
# ✅ Диаграммы построены

**Источник**: `<путь к исходнику>`
**Файл с диаграммами**: `<путь>/<имя>_diagrams.md`

## Диаграммы

| Диаграмма | Тип | Файлы | Рендер |
| --------- | --- | ----- | ------ |
| Сценарии использования | Use Case | `_spec-use-cases.puml` / `.svg` | ✅ |
| Модель статусов | State | `_spec-state-model.puml` | ⚠️ только исходник |

## Замечено в исходнике _(если есть)_

- <пробел или неоднозначность, всплывшая при рисовании> → `/simplegen.spec_check`

## Рендеринг _(если .svg не собраны)_

PlantUML не найден. Варианты:
- VS Code: расширение **PlantUML** — открыть `.puml`, `Alt+D` предпросмотр, экспорт в SVG;
- локально: установить `plantuml` (нужна Java) и повторить команду;
- внутренний сервер компании: задать `PLANTUML_SERVER` в `.env`.
```

## Особые случаи

- **Файл не найден** → `⚠️ Не найден файл <путь>.` + список доступных артефактов задачи.
- **Нет данных для диаграмм** → сообщить, какие триггеры не сработали, и предложить назвать нужный тип явно.
- **Нет `docs/theme.puml`** → построить без темы, предложить выполнить `simplegen init` для сидирования темы.
- **Файл занят другим процессом** → сообщить причину (открыт в редакторе, синхронизация) и попросить повторить.
