# Правила демо-прогона SimpleOne

Канон для команд `/simplegen.demo_plan`, `/simplegen.demo_data_prepare`, `/simplegen.demo_run`.
Здесь — **как** работать со стендом и браузером; **что** показывать описывает `_demo_plan.md`.

## Где запускается

- Только в **ветке задачи разработчика** — артефакты демо лежат рядом со спецификацией и уезжают в тот же MR.
- Стенд — из `SIMPLEONE_URL`. Прогон повторяют на стенде приёмки, сменив переменную; демо-план и
  `_demo_data.json` не меняются, демоданные создаются на каждом стенде заново.
- Задача должна быть задеплоена (`product_patch`), иначе прогон покажет старое поведение стенда.

## Работа с браузером (⚠️ КРИТИЧНО)

Демо воспроизводится **тем браузерным инструментом, который доступен агенту** в текущей IDE. Отдельный
браузерный сервер проект не ставит и не настраивает: `simplegen init` ничего для этого не прописывает.

- **Инструмента нет в списке доступных — не вызывать.** Это то же правило, что «не выдумывай методы
  API» из `project-core-rule`: сначала посмотреть, какие браузерные инструменты реально подключены, и
  работать только ими. Придуманное имя инструмента — такая же ошибка, как придуманный метод платформы.
- Имена вида `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type`,
  `browser_fill_form`, `browser_find`, `browser_wait_for`, `browser_take_screenshot`,
  `browser_evaluate` ниже по тексту — **типовые**: так называются инструменты у большинства браузерных
  серверов. Если у подключённого инструмента имена другие — работать его именами, смысл шагов тот же.
  Чего точно не существует нигде — `browser_fill` и `browser_search`: вместо них ввод в поле и поиск
  по тексту.
- Браузерных инструментов нет вообще — остановиться и сообщить пользователю
  (см. «Браузер недоступен»).

## Демоданные и демонстрация — это разные вещи (⚠️ КРИТИЧНО)

| Что | Чем делается | Видит ли зритель |
| --- | ------------ | ---------------- |
| **Предусловия** — то, что должно существовать до начала показа: демо-пользователи, роли, справочники, фоновые записи | `_demo_data.json` + `/simplegen.demo_data_apply` (Table API) | нет, это подготовка |
| **Демонстрация** — всё, что показывается заказчику: создание записей, кнопки, переходы состояний, согласования, виджеты, проверки доступа | **только UI в браузере** | да, это и есть демо |

**Во время `demo_run` любое демонстрируемое действие выполняется через интерфейс.** Нельзя создать запись
запросом к API и сказать «вот она появилась»: заказчик видит браузер, а не API, и демо обязано показать
ровно ту функциональность, которая описана в спецификации — форму создания, обязательные поля, кнопки,
переходы состояний, срабатывание бизнес-правил.

Если по демо-плану нужно создать заявку — агент открывает `/record/<table>`, заполняет поля через
`browser_fill_form` / `browser_type`, нажимает Save и проверяет результат на форме. Так же и для всего
остального: смена состояния — кнопкой, согласование — из интерфейса согласования, проверка ACL —
имперсонацией.

`browser_evaluate` допустим **только** для технической проверки состояния (кто я сейчас, текущий URL) и
для служебных вещей вроде экранного баннера. Демонстрируемую функциональность им подменять нельзя.

### Как адресовать элементы

Параметр `target` у `browser_click` / `browser_type` / `browser_evaluate` принимает **и** ref из снапшота,
**и** CSS-селектор. Для интерфейса SimpleOne всегда предпочитать устойчивый селектор по `data-test`:

```
[data-test="show-user-impersonate"]
```

Ref из `browser_snapshot` — только там, где `data-test` у элемента нет (строки списков, поля форм).

### Ритм работы

- `browser_snapshot` — перед действием по ref; для поиска одного элемента дешевле `browser_find`.
- `browser_wait_for` (`text` / `textGone` / `time` 1–3 с) после навигации и сохранения. Не ставить
  фиксированные длинные паузы.
- Одно и то же действие не повторять больше 2 раз без нового evidence.
- Скриншот — с явным именем файла вида `<task_id>_step<N>.png`; куда инструмент их складывает, зависит от IDE — путь взять из его ответа и указать в логе.

## Работа с формой записи

Формы SimpleOne размечены предсказуемыми `data-test` — по ним адресуются поля любой таблицы, без
догадок и без опоры на позицию элемента:

| Что | Селектор | Пример |
| --- | -------- | ------ |
| Обёртка поля (по подписи на форме) | `[data-test="field-<Label>"]` | `field-Assigned User` |
| Подпись поля | `[data-test="<column>-label"]` | `caller-label` |
| Строковое поле | `[data-test="<column>-field-string"]` | `number-field-string` |
| Текстовая область | `[data-test="<column>-field-textarea"]` | `subject-field-textarea` |
| Reference-поле | `[data-test="<column>-field-reference"]` | `caller-field-reference` |
| Choice-поле | `[data-test="<column>-field-select"]` | `priority-field-select` |
| Чекбокс | `[data-test="<column>-field-checkbox-checkbox"]` | `caller_is_consumer-field-checkbox-checkbox` |
| Кнопка Save | `[data-test="form_button__save-ui-button"]` | — |
| Кнопка Save and Exit | `[data-test="form_button__save_and_exit-ui-button"]` | — |
| Заголовок записи | `[data-test="heading-title"]` | — |

`<column>` — системное имя колонки из экспорта (`caller`, `assigned_user`, `subject`, `priority`),
`<Label>` — подпись, как она отображается на форме.

**Reference-поле** заполняется как это делает человек: `browser_click` по полю → `browser_type` фрагмента
названия → `browser_wait_for` появления подсказки → `browser_click` по нужной строке подсказки. Значение
нельзя «вписать» текстом: платформа хранит `sys_id`, и без выбора из справочника поле останется пустым.

**Choice-поле** — `browser_click` по контролу, затем `browser_click` по варианту с нужной подписью.
Подписи берутся из `choice-options` соответствующей таблицы.

**Проверять значения полей через `browser_evaluate`** (`target` — селектор поля, `function` —
`(element) => element.value`), а не поиском текста на странице: значение reference- и строкового поля
лежит в `value` инпута и в `innerText` страницы не попадает.

**После сохранения** проверять результат на форме: значения полей, состояние, заголовок записи
(`[data-test="heading-title"]`). Учесть, что номер (`number-field-string`) на форме создания платформа
подставляет **сразу**, до сохранения — сам по себе он не признак того, что запись сохранена.

## Авторизация

1. `browser_navigate` на `$SIMPLEONE_URL`.
2. `browser_snapshot` — если интерфейс уже загружен под нужным пользователем, шаг пропустить.
3. `browser_fill_form`: `[data-test="username-login-field"]` ← `$SIMPLEONE_LOGIN`,
   `[data-test="password-login-field"]` ← `$SIMPLEONE_PASSWORD`.
4. `browser_click` `[data-test="login-button"]`.
5. `browser_wait_for` — появление хедера/навигатора. Если виден `[data-test="login-error"]` — остановиться.

Учётные данные берутся из `.env` (`SIMPLEONE_URL`, `SIMPLEONE_LOGIN`, `SIMPLEONE_PASSWORD`) и **никогда**
не печатаются в чат, в `_demo_log.md` и в подписи к скриншотам.

## Имперсонация (⚠️ КРИТИЧНО)

Имперсонация — единственный способ показать демо под разными ролями: у таблицы `user` нет поля пароля
(только `password_hash`), поэтому логиниться под созданным демо-пользователем нельзя.

### Шаг 0. Запомнить себя (⚠️ ОБЯЗАТЕЛЬНО)

Сразу после авторизации, **до первой имперсонации**, получить и запомнить свой `sys_id`:

```js
async () => (await (await fetch("/v1/user/me", { credentials: "include" })).json()).data.sys_id
```

Это значение — единственный надёжный «я» на весь прогон. Держать его в контексте прогона и
использовать для каждого возврата.

> **⚠️ Не использовать `localStorage["x-impersonate"]` как признак себя.** Ключ выглядит подходящим, но
> при входе в имперсонацию **через UI** он перестаёт указывать на оператора: транзиентный 401 в момент
> смены сессии чистит ключи (`clearUserData`), а следующий `fetchUser` пересевает `x-impersonate` уже
> `sys_id` имперсонированного пользователя. Возврат по такому значению уводит не к себе, а к предыдущему
> демо-пользователю. Проверено на сборке `build.1465(b) + build.1283(f)`.

### Шаг 1. Проверить право

```bash
simplegen demo whoami
```

Нужен `impersonate_access: true`. Если `false`:

```markdown
❌ У учётной записи нет права имперсонации.
→ Выдайте роль `impersonator` пользователю из SIMPLEONE_LOGIN
→ Или проведите демо вручную по _demo_plan.md
```

### Шаг 2. Получить sys_id цели

1. Из `_demo_data.json` — поле `sys_id` записи демо-пользователя (заполняется `/simplegen.demo_data_apply`).
2. Иначе — `simplegen demo users --search "<имя или фрагмент>"`.
3. Пользователь не найден — **FAIL** шага с причиной «пользователь не создан», зависимые шаги — SKIP.
   Не подставлять «похожего» пользователя.

### Шаг 3. Переключиться — основной путь (UI)

1. `browser_click` `[data-test="header-option-item-user"]`
2. `browser_click` `[data-test="show-user-impersonate"]`
3. `browser_snapshot` — найти поле поиска в попапе (своего `data-test` у него нет), `browser_type` фрагмент имени
4. `browser_click` по пункту нужного пользователя внутри `[data-test="impersonate-list"]`
5. `browser_wait_for` — интерфейс перезагрузился под новым пользователем

Путь проверен на сборке `build.1465(b) + build.1283(f)`: цепочка кликов доводит до смены пользователя.

### Шаг 3-бис. Фолбэк (попап не открылся или пользователя нет в выдаче)

> **⚠️ Только из страницы, только с cookie-сессией.** Эндпоинт `/v1/impersonate` привязан к сессии
> браузера. Вызов того же эндпоинта с API-ключом (`Authorization: Bearer …`) **инвалидирует токен** —
> все последующие запросы получают 401. Поэтому имперсонацию делает только браузер; CLI (`simplegen
> demo …`) её не выполняет и выполнять не должен.

`browser_evaluate` тем же вызовом, что делает интерфейс платформы:

```js
async () => {
  const response = await fetch("/v1/impersonate?user_id=<sys_id>", { credentials: "include" });
  const body = await response.json();
  if (body.status === "OK") {
    window.localStorage.setItem("isImpersonateSession", "true");
    location.reload();
  }
  return body.status;
}
```

Затем `browser_wait_for` и `browser_snapshot` — убедиться, что в хедере другой пользователь.

### Шаг 4. Вернуться под себя (обязательно)

Возврат выполняется **в конце каждого блока имперсонации** и **в конце прогона** — в том числе когда шаг
провалился или прогон прерван.

**Основной путь — кнопка «Back to me» в меню пользователя.** Возврат — часть демонстрации, поэтому
делается интерфейсом:

1. Открыть меню пользователя. **Селектор зависит от интерфейса, в котором мы оказались:**
   - агентский — `[data-test="header-option-item-user"]`;
   - портал (сюда уводит пользователя без агентских ролей) — `.header__profile` внутри
     `[data-test="authheader-widget"]`.
   Надёжно: попробовать агентский селектор, при отсутствии — портальный.
2. Нажать пункт возврата. **Разметка тоже разная:**
   - портал — `[data-test="back-to-me"]`;
   - агентский интерфейс — `data-test` у пункта **нет**, выбирать по тексту из
     `dictionary.user_menu_titles.back_to_me` (в EN — `Back to me`); подпись берётся из `/v1/user/me`,
     поэтому работает и на русском интерфейсе.
   Надёжно: если `[data-test="back-to-me"]` есть в снапшоте — кликать его, иначе кликать по тексту.
3. `browser_wait_for` — интерфейс перезагрузился.

> Проверено на сборке `build.1465(b) + build.1283(f)`: в обоих интерфейсах меню под имперсонацией
> содержит `Profile`, `Impersonate`, `Logout`, `Back to me`, и клик по пункту возвращает к оператору.

**Фолбэк** (пункта нет в снапшоте) — `browser_evaluate` с `sys_id`, запомненным на Шаге 0:

```js
async () => {
  const self = "<свой sys_id с Шага 0>";
  const response = await fetch(`/v1/impersonate?user_id=${self}`, { credentials: "include" });
  const body = await response.json();
  if (body.status === "OK") {
    window.localStorage.setItem("isImpersonateSession", "false");
    location.reload();
  }
  return body.status;
}
```

После возврата **подтвердить смену пользователя** — `browser_snapshot` хедера или чтение `/v1/user/me`.
Не считать возврат успешным по факту клика: обработчик кнопки внутри платформы тоже опирается на
`localStorage["x-impersonate"]`, и при устаревшем значении вернёт к предыдущему демо-пользователю, а не к
оператору. Если `username` не совпал с оператором — выполнить фолбэк с `sys_id` с Шага 0 и записать это
в лог.

Перед началом прогона проверить, не осталась ли имперсонация от прошлого запуска: сравнить `username` из
`/v1/user/me` с `SIMPLEONE_LOGIN` (флаг `isImpersonateSession` — вспомогательный признак, он может врать).
Не совпало — сначала вернуться под себя.

> **Незакрытая имперсонация — источник каскада ложных FAIL**: все следующие шаги идут от чужого
> пользователя и упираются в ACL.

### Elevate (повышение ролей)

Отдельная от имперсонации механика: `[data-test="header-option-item-user"]` →
`[data-test="show-user-elevate"]` → включить нужные роли. По API тот же смысл несёт заголовок
`X-Elevated-Roles` (`SIMPLEONE_ELEVATED_ROLES` в `.env`). Elevate **не** заменяет имперсонацию:
он расширяет права текущего пользователя, а не меняет пользователя.

## Режим показа (демо на видеовстрече)

Прогон можно вести так, чтобы за ним следили люди — на созвоне, с шарингом экрана. Отличия от обычного
прогона только в подаче; шаги, селекторы и проверки те же.

> **⚠️ Прогон медленнее ручного показа** — после каждого действия агент сверяет состояние страницы.
> Штатный сценарий приёмки: прогнать заранее, записать окно, ускорить запись, наложить комментарий.
> Предупредить об этом на старте `--present`.

- **Браузер видимый.** Окно должно быть на экране, иначе показывать нечего: если инструмент умеет
  headless-режим, для показа он не годится.
- **Темп для человека.** После каждого шага пауза 3–4 с, чтобы зритель успел прочитать состояние и
  увидеть результат. Ввод в поля — посимвольно (`browser_type` с `slowly: true`), а не мгновенной вставкой.
- **Экранный баннер.** Перед каждым шагом обновлять поверх страницы плашку с номером и названием шага,
  текущим пользователем и короткой ремаркой «что здесь показываем». Ставится один раз через
  `browser_evaluate` и переустанавливается после каждой навигации. Крепить **снизу**: хедер SimpleOne
  `position: fixed`, и верхняя плашка его перекрывает.

```js
() => {
  let box = document.getElementById("__sg_demo");
  if (!box) {
    box = document.createElement("div");
    box.id = "__sg_demo";
    box.style.cssText = "position:fixed;z-index:2147483647;bottom:0;left:0;right:0;padding:10px 16px;" +
      "background:#0f172a;color:#fff;font:14px/1.45 Segoe UI,Arial,sans-serif;pointer-events:none";
    document.body.appendChild(box);
  }
  box.textContent = "Шаг N из M — <название> · под пользователем: <username>";
}
```

- **Подсветка перед действием.** Перед клика́ми по ключевым элементам (меню пользователя, пункт
  имперсонации, строка списка) обвести элемент рамкой на ~1.5 с — зритель видит, куда идёт клик.
- **Проговаривать неочевидное.** Смена пользователя и возврат под себя — самое непонятное для зрителя
  место прогона: держать в баннере, под кем идёт текущий шаг, и отдельно отмечать момент возврата.
  Если возврат пришлось делать фолбэком (Шаг 4), это тоже написать — иначе выглядит как «магия за кадром».
- **Отдельное окно.** Окно показа не должно делить процесс с рабочим браузером оператора: закрытие
  постороннего окна убивает прогон. Перед показом закрыть лишние вкладки в окне прогона.
- **Кадры шагов.** Скриншот с именем вида `<task_id>_present_step<N>.png` — из них собирается отчёт
  после встречи.

## Проверки ожидаемых результатов

| Формулировка в демо-плане | Как проверять |
| ------------------------- | ------------- |
| «отображается …», «появляется …» | `browser_find` по тексту; при необходимости `browser_snapshot` |
| «не отображается …», «отсутствует …» | `browser_find` → пусто, либо `browser_wait_for` с `textGone` |
| «статус = …», «значение = …» | `browser_snapshot` и сверка значения поля |
| «URL содержит …» | `browser_evaluate` → `() => location.href` |
| «кнопка недоступна» | `browser_snapshot` — элемента нет либо он `disabled` |
| «доступ запрещён» (после имперсонации) | ожидаемый результат — заглушка или пустой список, а не ошибка прогона |

Проверку формулировать так, чтобы её результат был однозначным PASS или FAIL. Если шаг демо-плана описан
слишком расплывчато для автоматической проверки — зафиксировать в логе SKIP с причиной «требует визуальной
оценки», а не выдавать PASS «на глаз».

## Демоданные

- Демоданные — это **runtime-записи** (`employee`, `sys_user_has_role`, записи бизнес-таблиц), а не DSL.
  Их создание на стенде через `/simplegen.demo_data_apply` — разрешённое исключение из запрета «не менять стенд
  напрямую» (`project-core-rule`, раздел «Деплой»). Конфигурация по-прежнему только через `product_patch`.
- Имена таблиц, колонок и допустимые значения брать **из экспорта** (`platform/data-structure/columns/`,
  `sa/`, `<product>/domain/`), никогда не выдумывать. Пример реальных полей: у `sys_user_has_role` это
  `user_id` и `role_id` (обе mandatory), а не `user` / `role_name`.
- Обязательные поля определяются по `"mandatory": true` в экспорте колонок. Для `employee` (наследует
  `user`) это как минимум `username`, `email`, `timezone_id`. Reference-поля требуют `sys_id`, а не имя:
  `timezone_id` — это ссылка на `sys_timezone`.
- **Запись в `sys_user_has_role` требует elevated-роли.** Без неё Table API отвечает
  `Unable to create a record in the "User Role" table due to the ACL restrictions`. Решение —
  `SIMPLEONE_ELEVATED_ROLES=security_admin` в `.env`.
- Имперсонация **не используется** для правки конфигурации — только для просмотра и демонстрации.

## Повторный прогон на том же стенде

Стенд между прогонами **не очищается**: автоматической очистки нет, команды `demo cleanup` не существует —
не выдумывать.

- Предусловия из `_demo_data.json`: `/simplegen.demo_data_apply` пропускает записи с заполненным `sys_id` — дублей нет.
- Записи, создаваемые шагами демонстрации в UI: создаются заново каждый прогон — **дубли ожидаемы**.
  Шаг «открыть запись с …» открывает **последнюю созданную**, в логе отметить, что запись не единственная.
- Записи со стенда **не удалять** — это решение человека. Если остатки блокируют шаг (уникальность,
  запись уже в конечном состоянии) — FAIL с причиной «остатки предыдущего прогона» и в рекомендациях
  указать, что удалить вручную.
