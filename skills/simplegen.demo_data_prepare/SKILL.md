## Назначение

> **⚡ BETA**: Эта команда находится в стадии бета-тестирования. Формат `_demo_data.json` может измениться в будущих версиях. Проверяйте сгенерированные данные перед использованием.

Команда `/simplegen.demo_data_prepare` генерирует файл `_demo_data.json` с описанием runtime-записей, необходимых для проведения демонстрации:
- Читает блок «Демоданные» из `_demo_plan.md`
- Анализирует `_spec.md` и `domain/` для уточнения таблиц и полей
- Формирует структурированный JSON с записями для создания на стенде
- Выделяет шаги, которые невозможно автоматизировать (SOP, workflow), в отдельный блок `manual_steps`

`_demo_data.json` — **не** DSL-файл конфигурации. Это описание runtime-записей (сотрудники, задачи, записи в бизнес-таблицах), которые нужны только для демонстрации функционала.

> **Разграничение**: DSL в `domain/` описывает **конфигурацию** (таблицы, колонки, ACL, скрипты, виджеты). `_demo_data.json` описывает **данные** (записи в таблицах, пользователи, роли), необходимые для показа работы этой конфигурации.
>
> **Порядок работы**: команда генерирует `_demo_data.json`. Дальше `/simplegen.demo_data_apply` создаёт записи на стенде (ручные шаги из блока `manual_steps` выполняются человеком), и `/simplegen.demo_run` воспроизводит блок «Демонстрация».

> **⚠️ В файл попадают только ПРЕДУСЛОВИЯ.** `_demo_data.json` описывает то, что должно существовать
> **до** начала показа: демо-пользователей, их роли, справочники, фоновые записи. Функциональность самой
> задачи в него **не выносится**: если задача про создание заявки, согласование или переход состояния —
> это шаги демонстрации, и на демо они выполняются в интерфейсе (`demo-rules`: «Демоданные и демонстрация
> — это разные вещи»). Подложить результат через API и показать «вот оно уже есть» — значит не показать
> требование.

> **⚠️ У демо-пользователя нет пароля.** В таблице `user` нет поля пароля (только `password_hash`), поэтому войти на стенд под созданным демо-пользователем невозможно. Единственный способ показать функционал под его ролями — **имперсонация** (канон — `demo-rules`). Не генерировать в демоданные поля вида `password` и не описывать в демо-плане вход по логину демо-пользователя.

JSON-файлы метаданных задачи (`simplegen.json`) НЕ изменяются.

> **Примечание**: `<product>` в этом документе означает любой продукт, включая `sa/` с вендорскими правами.

## Алгоритм работы

### Шаг 0: Проверить версию simplegen (⚠️ ОБЯЗАТЕЛЬНО)

Сравнить `version` (`.simplegen/state.json`) с выводом `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; CLI выше — `/simplegen.init`; совпадают — продолжить. Правило (канон) — `project-core-rule` (always-on).

### Шаг 1: Загрузить контекст задачи

1. Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`)
2. Загрузить `<product>/<current_feature_path>/_demo_plan.md` — полностью
3. Если `_demo_plan.md` не найден — ошибка:
   ```
   ⚠️ Демо-план `_demo_plan.md` не найден.
   → `/simplegen.demo_plan` — сформировать демо-сценарий
   ```
4. Загрузить `<product>/<current_feature_path>/_spec.md` — полностью (для уточнения полей и значений)
5. Если `_spec.md` не найдена — предупредить, продолжить только по `_demo_plan.md`:
   ```
   ⚠️ Спецификация `_spec.md` не найдена. Демоданные будут построены только по демо-плану.
   → Рекомендуется сначала `/simplegen.spec_create`
   ```

### Шаг 2: Загрузить реализованный код (domain/)

Демоданные генерируются **для текущей ветки разработки** — они должны взаимодействовать с конкретными сущностями, созданными/изменёнными в рамках задачи. Поэтому необходим глубокий анализ `domain/`, а не только валидация имён полей.

1. Просканировать `<product>/domain/` — определить фактически созданные/изменённые сущности
2. Извлечь из DSL-файлов:
   - **Таблицы и колонки** (`domain/data-structure/tables/`, `domain/data-structure/columns/`) — имена таблиц, типы колонок, обязательные поля, значения по умолчанию
   - **Choice-опции** (`domain/data-structure/choice-options/`) — допустимые значения для полей типа Choice (использовать в `fields`)
   - **State-модели и переходы** (`domain/data-structure/state-models/`, `domain/data-structure/state-transitions/`) — допустимые состояния записей, начальные состояния
   - **Роли** (`domain/access-control/roles.ts`) — точные имена ролей для `sys_user_has_role`
   - **ACL-записи** (`domain/access-control/security-acls/`) — какие роли нужны для доступа к каким таблицам и операциям (определяет набор демо-пользователей)
   - **Бизнес-правила** (`domain/business-logic/business-rules/`) — какие поля обязательны, какие вычисляются автоматически (не заполнять вычисляемые поля)
   - **Клиентские скрипты** (`domain/business-logic/client-scripts/`) — какие поля триггерят клиентскую логику (учитывать при задании значений)
   - **Системные свойства** (`domain/business-logic/system-properties.ts`) — имена и значения для записей `sys_property`
   - **Формы** (`domain/forms/`) — какие поля видны на форме (помогает определить, какие поля нужно заполнить для демонстрации)
   - **Навигация** (`domain/navigation/`) — пункты меню, используемые в демо-шагах

3. **Сопоставить демоданные с реализацией**:
   - Для каждой таблицы из блока «Демоданные» — проверить, существует ли она в DSL или это платформенная таблица
   - Для каждого поля — проверить тип (string, integer, reference, choice, boolean), использовать допустимые значения
   - Для reference-полей — определить целевую таблицу из DSL (какой тип записи ожидается)
   - Для choice-полей — использовать **только** значения из `choice-options`, не произвольные строки
   - Для state-полей — использовать начальное состояние из state-model (если не указано иное в демо-плане)
   - Обязательные поля из бизнес-правил — обязательно заполнить, даже если не упомянуты в демо-плане

4. Если `domain/` пуст или не содержит изменений — предупредить, продолжить без валидации:
   ```
   ⚠️ Код для задачи ещё не сгенерирован. Демоданные будут сгенерированы без анализа реализации.
   Поля, типы и допустимые значения не будут валидироваться.
   → Рекомендуется сначала `/simplegen.code_generate`
   ```

### Шаг 3: Извлечь блоки «Демо-пользователи» и «Демоданные»

1. Найти секцию `## Демо-пользователи` — таблицу «имя → роли → что демонстрируется». Это источник
   массива `users[]` и записей `employee` + `sys_user_has_role`. Имя переносить **буквально**: по нему
   идут шаги имперсонации и поиск пользователя при прогоне. Таблицы нет, а шаги имперсонации в
   демо-плане есть — предупредить и собрать пользователей по именам из этих шагов
2. Найти секцию `## Демоданные` (или `Демоданные.` / `Предусловие:`) в `_demo_plan.md`
3. Извлечь весь текст до следующего заголовка `## Демонстрация` (или `Демонстрация.` / `Сценарий:` / `---`)
4. Если блок «Демоданные» не найден или пуст — ошибка:
   ```
   ⚠️ Блок «Демоданные» не найден в _demo_plan.md.
   
   Убедитесь, что демо-план содержит секцию «Демоданные»:
   → `/simplegen.demo_plan` — пересоздать демо-план
   ```

### Шаг 4: Проверить идемпотентность

Если файл `<product>/<current_feature_path>/_demo_data.json` уже существует:

```markdown
⚠️ Файл `_demo_data.json` уже существует.

Варианты:
A) Перезаписать
B) Пропустить
C) Объединить (добавить новые записи, не трогая существующие)

Ответьте: A / B / C
```

- **A)** — полностью перезаписать файл
- **B)** — прекратить выполнение, оставить существующий файл
- **C)** — прочитать существующий файл, добавить только записи с новыми alias (если alias совпадает — оставить существующую запись)

**Режим ultra** (`--ultra` в аргументах — вызов из `/simplegen.ultra`, канон — `ultra-rules`):
- Шаг 0 пропустить — версию проверил оркестратор;
- здесь не спрашивать и выбрать **C)**: повтор этапа не теряет `sys_id` уже созданных записей;
- не генерировать запись `impersonator` и любые `sys_user_has_role`, где `user_id` — не `$alias` демо-пользователя этого файла. Не генерировать `sys_property`. Такие пункты — в `manual_steps`: согласие на интервью покрывает демоданные, а не права учётки прогона и конфигурацию;
- тестовые данные на стенде — записи `[TEST <task_id>]` от тестов и записи, которые человек или агент создали для воспроизведения, — демоданными не считаются и при их генерации игнорируются: не переиспользовать, не ссылаться на них, не пропускать из-за них генерацию. Демоданные — свой набор с `$alias`;
- итог вернуть оркестратору.

### Шаг 5: Классифицировать пункты демоданных

Для каждого пункта из блока «Демоданные» определить категорию:

| Категория                | Действие                   | Паттерны в тексте                                                                        |
| ------------------------ | -------------------------- | ---------------------------------------------------------------------------------------- |
| SOP-зависимости          | `manual_step`              | "Загрузить SOP...", "Загрузить подготовленный файл...", "/record/sys_vcs_retrieved_pack" |
| Пользователи/сотрудники  | Запись `employee`          | "Создать записи в таблице Сотрудник...", "создать запись...; (/record/employee)"         |
| Назначение ролей         | Запись `sys_user_has_role` | "Выдать пользователю роль...", "Выдать...все роли"                                       |
| Право имперсонации       | Запись `sys_user_has_role` с ролью `impersonator` | Демо-план содержит шаги имперсонации, а у учётной записи прогона права нет |
| Записи в бизнес-таблицах | Запись в указанной таблице | "Создать записи в таблице ... с полями; (/record/[table])"                               |
| Системные свойства       | Запись `sys_property`      | "Установить системное свойство...", "sys_property"                                       |
| Workflow/согласование    | `manual_step`              | "Создать workflow...", "Approval Type...", "Настроить участников..."                     |
| Делегирование            | `manual_step`              | "Создать запись делегирования..."                                                        |
| Импорт данных            | `manual_step`              | "Импортировать демо-данные...", "Загрузить СОП с ранее подготовленными записями"         |
| Прочее сложное           | `manual_step`              | Любое неструктурированное многошаговое действие                                          |

### Шаг 6: Сформировать записи

Для каждого автоматизируемого пункта:

#### 6.1: Определить таблицу

- Из URL в скобках: `(/record/employee)` → таблица `employee`
- Из текста: "в таблице задачи" → таблица `task`
- Из контекста `_spec.md` и `domain/` — уточнить кастомные таблицы продукта
- **Приоритет**: если таблица описана в `domain/data-structure/tables/` — использовать точное имя из DSL
- Если таблица не определена — пометить `manual_step` с причиной

#### 6.2: Определить alias

- Уникальный snake_case идентификатор для каждой записи
- Для пользователей — на основе имени: "User Manager" → `user_manager`
- Для записей в таблицах — на основе ключевого поля: "subject: Согласованная задача" → `task_agreed`
- Для ролей — комбинация пользователя и роли: `user_manager_role_knowledge_agent`

#### 6.3: Определить поля

> **⚠️ Имена полей только из экспорта.** Каждое имя поля должно существовать в `platform/data-structure/columns/<table>.ts`, `sa/domain/data-structure/columns/` или `<product>/domain/data-structure/columns/`. Суффикс `_id` у reference-полей **не добавляется и не убирается по догадке**: на платформе есть и `user_id`/`role_id`/`group_id`, и `manager`/`unit` без суффикса. Поля, которого нет в экспорте, в `fields` быть не должно.

- **Текстовые значения**: из демо-плана или `_spec.md` — конкретные значения, **НИКОГДА** placeholder-ы
- **Reference-поля**: `$alias` нотация — ссылка на другую запись по alias
  - Пример: `"assigned_to_id": "$user_manager"` — при применении разрешится в sys_id сотрудника
  - Пример: `"manager": "$user_manager"` — reference на другую запись employee (у этой колонки суффикса `_id` нет)
  - Точное имя колонки и целевую таблицу брать из экспорта колонок
- **Choice-поля**: использовать **только** значения из `choice-options/`. Если в демо-плане указано значение, не совпадающее с choice — предупредить и подставить ближайшее
- **State-поля**: использовать начальное состояние из `state-models/`, если демо-план не требует иного состояния
- **Boolean-поля**: `true` / `false` (не строки)
- **Integer/Decimal-поля**: числовые значения (не строки)
- **Роли**: для `sys_user_has_role` — **`user_id`** и **`role_id`** (обе колонки mandatory). `user_id` — `$alias` сотрудника, `role_id` — `$alias` записи роли либо имя роли строкой (`/simplegen.demo_data_apply` разрешит его через `sys_role.name`). **Проверить существование роли** в `platform/access-control/roles.ts` или `<product>/domain/access-control/roles.ts`
- **Обязательные поля**: заполнить все колонки с `"mandatory": true` из экспорта, даже если они не упомянуты в демо-плане. Для `employee` (наследует `user`) это как минимум `username`, `email`, `timezone_id` (последнее — reference на `sys_timezone`, значением идёт `sys_id`). Дополнительно учесть обязательность, навязанную бизнес-правилами в `business-logic/business-rules/`
- **Вычисляемые поля**: если поле заполняется автоматически (серверным скриптом, бизнес-правилом) — **НЕ включать** в `fields`, иначе вычисленное значение будет перезаписано
- **Пароли**: поля пароля не существует — **никогда** не генерировать `password`. Вход под демо-пользователем невозможен, доступ показывается имперсонацией
- **Валидация**: проверить, что все указанные поля существуют в экспорте колонок таблицы. Несуществующие поля — предупредить в выводе и не включать в файл

#### 6.4: Определить зависимости

- Если запись ссылается на другую через `$alias` — добавить `depends_on: ["alias"]`
- Упорядочить записи: зависимости раньше зависимых
- Пример: `employee` раньше `sys_user_has_role` раньше `task` (если task ссылается на пользователя)

### Шаг 7: Сформировать ручные шаги

Для каждого пункта, классифицированного как `manual_step`:

- `order` — порядок выполнения среди ручных шагов
- `description` — текст из демо-плана (оригинальная формулировка)
- `url` — URL на стенде, если указан (например `/record/sys_vcs_retrieved_pack`)
- `reason` — краткое пояснение, почему шаг не автоматизирован

### Шаг 8: Записать _demo_data.json

Записать в `<product>/<current_feature_path>/_demo_data.json`.

JSON-файлы метаданных задачи (`simplegen.json`) НЕ изменяются.

## Формат _demo_data.json

```json
{

  "description": "Демоданные для задачи [task_id]: [Название фичи]",
  "source": "_demo_plan.md",
  "generated_at": "2026-04-09T12:00:00Z",
  "domain_context": {
    "tables": ["task", "employee"],
    "roles": ["knowledge_agent", "task_manager"],
    "choice_fields": {
      "task.priority": ["low", "medium", "high", "critical"],

    },
    "required_fields": {
      "employee": ["username", "email", "timezone_id"],
      "task": ["subject", "assigned_to_id"]
    }
  },
  "users": [
    {
      "alias": "user_manager",

    }
  ],
  "records": [
    {
      "alias": "user_manager",

        "username": "demo_user_manager",

      "fields": {
        "user_id": "$user_manager",
        "role_id": "knowledge_agent"
      },
      "depends_on": ["user_manager"]
    },
    {
      "alias": "second_user",
      "table": "employee",
      "sys_id": null,
      "fields": {
        "username": "demo_second_user",
        "first_name": "Second",
        "last_name": "User",
        "email": "second.user@demo.local",
        "timezone_id": "166189441111831205",

      },

    },
    {
      "alias": "task_important",
      "table": "task",
      "sys_id": null,
      "fields": {
        "subject": "Очень важная задача",
        "assigned_to_id": "$second_user",
        "priority": "critical",
        "state": "new"
      },

```

> **Reference-поля требуют `sys_id`, а не имя.** `timezone_id` — ссылка на `sys_timezone`, поэтому в него подставляется `sys_id` записи часового пояса (найти: `/list/sys_timezone` или чтение Table API `sys_timezone` с `sysparm_query=name=Europe/Moscow`, см. `table-api-rules`), а не строка `"UTC"`. Единственное исключение — `sys_user_has_role.role_id`: там допустимо имя роли, `/simplegen.demo_data_apply` сам найдёт `sys_id`.

> **Записи `sys_user_has_role` требуют elevated-роли.** Без неё Table API отвечает `Unable to create a record in the "User Role" table due to the ACL restrictions`. Решение — `SIMPLEONE_ELEVATED_ROLES=security_admin` в `.env`.

> `sys_id: null` заполняется командой `/simplegen.demo_data_apply` после создания записи. `/simplegen.demo_run` читает эти значения, чтобы имперсонироваться под нужного пользователя и открывать записи по прямому URL. Уже заполненный `sys_id` означает, что запись создана — повторный `apply` её пропустит.

### Нотация $alias

Значения полей, начинающиеся с `$`, — это ссылки на другие записи в том же файле:

- `"assigned_to_id": "$user_manager"` — reference на запись с alias `user_manager`
- `/simplegen.demo_data_apply` разрешает `$alias` в `sys_id` созданной записи
- При ручном создании на стенде — найти запись по её полям и подставить вручную

### Роли (`sys_user_has_role`)

Колонки таблицы — `user_id` и `role_id`, **обе mandatory**:

- `"user_id": "$user_manager"` — reference на запись `employee`
- `"role_id": "knowledge_agent"` — имя роли строкой; `/simplegen.demo_data_apply` находит `sys_id` через `sys_role.name`
- Имя роли обязательно сверить с `platform/access-control/roles.ts` или `<product>/domain/access-control/roles.ts`

## Правила формирования записей

### Общие

- **Контекст ветки** — демоданные генерируются строго под текущую ветку разработки. Все имена таблиц, колонок, choice-значений и ролей берутся из `domain/` текущей задачи
- **Конкретные значения** — НИКОГДА не использовать placeholder-ы типа "[заполнить]", "[значение]"
- **Минимально достаточный набор** — только записи-предусловия. Если запись создаётся по шагам демо-плана
  в интерфейсе, её в `records` быть не должно
- **Осмысленные данные** — если значение не указано в демо-плане, генерировать реалистичное, согласованное с типами полей из DSL
- **Системные имена таблиц** — использовать `employee`, не "Сотрудник"; `task`, не "Задача"
- **Уникальные alias** — каждый alias уникален в пределах файла, формат snake_case
- **Типы данных** — соблюдать типы из DSL: string → строка, integer → число, boolean → true/false, choice → одно из допустимых значений, reference → `$alias`

### Пользователи (employee)

- Для каждой уникальной роли из демо-плана — отдельная запись employee
- Если ACL в `access-control/security-acls/` требуют определённых ролей — создать пользователей с этими ролями, даже если прямо не указано в демо-плане
- **Обязательные поля** (наследуются от `user`): `username`, `email`, `timezone_id`. Плюс осмысленные `first_name` / `last_name` — по ним идёт поиск при имперсонации
- `username` — snake_case, с префиксом `demo_`, чтобы демо-пользователи отличались от реальных
- `email` генерировать как `<имя>@demo.local`
- Reference на менеджера — колонка `manager` (без суффикса `_id`): `"manager": "$alias_другого_employee"`
- **Пароль не задаётся** — его поля не существует; доступ демонстрируется имперсонацией
- Отдельная запись `sys_user_has_role` для привязки каждой роли
- Каждого пользователя продублировать в блоке `users[]` — оттуда `demo_run` берёт имя для имперсонации

### Назначение ролей (sys_user_has_role)

- `user_id` — reference на employee: `"$alias_employee"`
- `role_id` — имя роли строкой **из `access-control/roles.ts`** (приоритет над текстом демо-плана)
- Если "Выдать все роли" — создать по одной записи для каждой роли из `<product>/domain/access-control/roles.ts`
- Если демо-план содержит имперсонацию, а у учётной записи прогона нет права — добавить запись с ролью `impersonator`

### Записи в бизнес-таблицах

- Таблица из URL: `(/record/task)` → `"table": "task"`
- Поля из текста: `subject: Согласованная задача` → `"subject": "Согласованная задача"`
- Reference-поля: точное имя колонки — из экспорта (например `assigned_to_id`), значение — `$alias`
- **Choice-поля**: использовать только значения из `choice-options/` для данной таблицы
- **State-поля**: начальное состояние из `state-models/`, если демо-план не требует другого
- **Обязательные поля**: заполнять все колонки с `"mandatory": true` в экспорте, а также поля, помеченные обязательными в бизнес-правилах (`business-logic/business-rules/`)

### Системные свойства (sys_property)

- `"table": "sys_property"`
- Поля: `name`, `value`, `description`
- Имена свойств — из `domain/business-logic/system-properties.ts` или из контекста _spec.md

## Загрузка контекста

Перед работой обязательно:
1. **`demo-rules`** — канон демоданных и имперсонации (какие поля брать из экспорта, почему нет пароля)
2. **`_demo_plan.md`** — полностью (блок «Демоданные» и «Демонстрация» для понимания контекста)
3. **`_spec.md`** — полностью (UC, FR, модель данных, роли, состояния)
4. **`platform/data-structure/columns/`** и **`sa/domain/data-structure/columns/`** — точные имена и обязательность колонок платформенных таблиц (`user`, `employee`, `sys_user_has_role`)
5. **`<product>/domain/`** — **полный анализ реализации текущей ветки**:
   - `domain/data-structure/tables/` — какие таблицы создаются/изменяются
   - `domain/data-structure/columns/` — какие колонки с какими типами, обязательность, reference-таблицы
   - `domain/data-structure/choice-options/` — допустимые значения для choice-полей
   - `domain/data-structure/state-models/` — модели состояний, начальные/конечные состояния
   - `domain/data-structure/state-transitions/` — допустимые переходы между состояниями
   - `domain/access-control/roles.ts` — имена и описания ролей
   - `domain/access-control/security-acls/` — какие роли нужны для доступа к таблицам
   - `domain/business-logic/business-rules/` — обязательные поля, вычисляемые поля
   - `domain/business-logic/system-properties.ts` — системные свойства
   - `domain/forms/` — видимые поля на формах
   - `domain/navigation/` — пункты меню
6. **`<product>/AGENTS.md`** — контекст продукта
7. **`_demo_data.json`** — если существует (для объединения)
8. **`_task_plan.md`** — при наличии, для понимания архитектуры реализации

## Применение демоданных на стенде

Применяет отдельная команда `/simplegen.demo_data_apply`. Что она делает:
- сортирует записи по `depends_on` (зависимости создаются раньше зависимых);
- отправляет `POST /rest/v1/table/<table>` с полями записи;
- разрешает `$alias` в `sys_id` уже созданных записей;
- для `sys_user_has_role.role_id` находит роль по имени через `sys_role.name`;
- записывает полученный `sys_id` в `_demo_data.json`;
- записи с уже заполненным `sys_id` **пропускает** — повторный запуск не создаёт дублей;
- `manual_steps` не выполняет, а печатает списком.

> Создание runtime-демоданных на стенде — разрешённое исключение из запрета «не менять стенд напрямую» (`project-core-rule`, раздел «Деплой»). На DSL-конфигурацию исключение не распространяется.
