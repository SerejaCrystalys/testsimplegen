## Назначение

Команда `/simplegen.demo_plan` формирует демо-сценарий задачи:
- Читает `_spec.md`, `_task_plan.md` и реализованный код в `domain/`
- Формирует **блок демоданных** (загрузка SOP, создание пользователей, ролей, записей в таблицах, настройка workflow и т.д.)
- Формирует **блок демонстрации** (пошаговый нарративный сценарий показа функционала)
- **Полностью перезаписывает** `_demo_plan.md`

`_demo_plan.md` — derived-артефакт, пересобирается из `_spec.md` и реализованного кода.

> **Разграничение**: `_spec.md` описывает **ЧТО** (UC, FR, модель данных, доступы, UI). `_task_plan.md` описывает **КАК** (фазы, задачи, файлы). `_demo_plan.md` описывает **ЧТО ПОКАЗАТЬ** (подготовка данных + последовательность действий для демонстрации).
>
> **Порядок работы**: после генерации `_demo_plan.md` подготовьте демоданные через `/simplegen.demo_data_prepare`, примените их на стенде через `/simplegen.demo_data_apply`, затем запустите `/simplegen.demo_run` для автоматического воспроизведения блока «Демонстрация».

> **⚠️ Доступ под другой ролью показывается только имперсонацией.** У таблицы `user` нет поля пароля, войти на стенд под демо-пользователем нельзя. Поэтому шаги вида «войти как …» недопустимы — только «Имперсонироваться под …». Канон — `demo-rules`.

JSON-файлы НЕ изменяются.

> **Примечание**: `<product>` в этом документе означает любой продукт, включая `sa/` с вендорскими правами.

## Алгоритм работы

### Шаг 0: Проверить версию simplegen (⚠️ ОБЯЗАТЕЛЬНО)

Сравнить `version` (`.simplegen/state.json`) с выводом `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; CLI выше — `/simplegen.init`; совпадают — продолжить. Правило (канон) — `project-core-rule` (always-on).

### Шаг 1: Загрузить контекст задачи

1. Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`)
2. Загрузить `<product>/<current_feature_path>/_spec.md` — полностью
3. Загрузить `<product>/<current_feature_path>/_task_plan.md` — полностью
4. Если `_spec.md` не найдена — ошибка:
   ```
   ⚠️ Спецификация `_spec.md` не найдена.
   → `/simplegen.spec_create` — создать спецификацию
   ```
5. Если `_task_plan.md` не найден — предупредить, продолжить только по `_spec.md`:
   ```
   ⚠️ План `_task_plan.md` не найден. Демо-план будет построен только по спецификации.
   → Рекомендуется сначала `/simplegen.spec_plan`
   ```

### Шаг 2: Загрузить реализованный код (domain/)

1. Просканировать `<product>/domain/` — определить фактически созданные/изменённые сущности
2. Извлечь из DSL-файлов:
   - **Таблицы и колонки** (с типами, choices) — для формирования записей в демоданных
   - **ACL-записи** (какие роли, какие таблицы, какие операции) — для определения демо-пользователей и проверки доступов
   - **Бизнес-правила и клиентские скрипты** (условия срабатывания) — для формирования шагов, которые триггерят логику
   - **Виджеты** (имена, опции) — для демонстрации виджетного функционала
   - **UI Actions** — для шагов с кнопками на форме
   - **Меню навигатора** — для шагов навигации
   - **Формы и списки** — для проверки отображения полей
   - **Workflow и state model** (если есть) — для шагов с переходами состояний
   - **Роли** — для списка демо-пользователей

Демоданные должны основываться на **реально созданных** сущностях, а не только на спецификации.

### Шаг 3: Сформировать блок "Демоданные"

Из `_spec.md` и `domain/` определить всё необходимое для воспроизведения сценария:

#### 3.1: Зависимости от SOP

- Если задача зависит от других задач — указать загрузку SOP через `/record/sys_vcs_retrieved_pack`
- SOP текущей задачи: `Загрузить SOP задачи [<PRODUCT>]_<task_id> и все файлы зависимых задач; (/record/sys_vcs_retrieved_pack)`

#### 3.2: Пользователи и роли

Из ACL-записей в `domain/access-control/` и ролей в `domain/access-control/roles.ts` определить:
- Какие роли задействованы
- Для **каждой уникальной роли** — создать демо-пользователя с конкретным именем
- Формат: `Создать записи в таблице Сотрудник (/record/employee):` с перечислением пользователей и ролей
- Если в `_spec.md` упомянуты конкретные пользовательские роли (матрица доступов) — использовать их
- Сформировать **обязательную таблицу «Демо-пользователи»** (имя → роли → что демонстрируется). Она — источник для `_demo_data.json` и для шагов имперсонации
- Если демонстрация требует имперсонации, а учётная запись прогона ею не обладает — добавить в демоданные выдачу роли `impersonator`

#### 3.3: Записи в таблицах

Из Use Cases и FR определить:
- Какие записи нужны для прохождения сценариев
- Указать **конкретные значения полей** (из UC или сгенерировать осмысленные)
- Формат: `Создать записи в таблице [title] с полями (/record/[table_name]):` + перечисление

#### 3.4: Workflow и состояния

Если задача затрагивает workflow или state model:
- Указать настройку workflow с действиями
- Описать участников (если approval)
- Указать начальные состояния записей

#### 3.5: Системные настройки

Если задача создаёт system properties:
- Указать значения системных свойств для демонстрации

**⚠️ ПРАВИЛА формирования демоданных:**
- Каждая запись — с конкретным URL создания (`/record/<table_name>`)
- Для пользователей — конкретные имена и роли через `/record/employee`
- Данные должны быть **минимально достаточными** для всех сценариев демонстрации
- **НИКОГДА** не использовать абстрактные placeholder-ы типа "[заполнить]" — только конкретные значения
- Если значения не указаны в `_spec.md` — генерировать осмысленные примеры

### Шаг 4: Сформировать блок "Демонстрация"

Из Use Cases (основные и ALT-потоки) и FR построить нарративные шаги:

#### 4.1: Структура шагов

- Нумерованный список (1, 2, 3...)
- Каждый шаг — **действие** в повелительном наклонении
- Ожидаемые результаты — **вложенные подпункты** (маркированный список с `-`)
- Подшаги — через вложенную нумерацию (1.1, 1.2) или подпункты

#### 4.2: Типы действий

| Действие в демо-плане | Пример                                                         |
| --------------------- | -------------------------------------------------------------- |
| Навигация через URL   | `Перейти на листовое представление таблицы задач (/list/task)` |
| Навигация через меню  | `В меню навигатора выбрать пункт [категория] > [элемент]`      |
| Открытие записи       | `Открыть запись задачи с subject: [значение]`                  |
| Создание записи       | `Перейти на форму создания записи (/record/<table>)`           |
| Действие с формой     | `Нажать кнопку "[название]"`                                   |
| Заполнение полей      | `Указать в поле {field} значение "[value]"`                    |
| Имперсонация          | `Имперсонироваться под [Имя пользователя] ([role_name])`       |
| Возврат под себя      | `Вернуться под себя`                                           |
| Демонстрация виджета  | `Продемонстрировать виджет [название]`                         |
| Демонстрация ACL      | `Продемонстрировать ACL` (через имперсонацию под разные роли)  |
| Демонстрация свойств  | `Продемонстрировать системные свойства`                        |

#### 4.3: Правила формирования

> **Демо-план строится под конкретную задачу.** Единственный источник того, что показывать, — `_spec.md`
> этой задачи: её UC, FR, модель данных, матрица доступов и UI. Не переносить структуру шагов из другой
> задачи и не сводить показ к «открыли список — открыли запись». Заказчик и команда ждут, что увидят
> каждое заявленное требование в работе.

> **Разделяй предусловия и показ.** В блок «Демоданные» попадает только то, что должно существовать
> **до** начала демонстрации (пользователи, роли, справочники, фоновые записи). Всё, что составляет саму
> функциональность задачи, идёт шагами в блок «Демонстрация» и выполняется в интерфейсе: если задача про
> создание заявки — на демо заявка **создаётся через форму**, а не подкладывается заранее.

- **Все FR с пользовательски-видимым поведением** обязательно покрыты шагами
- **ACL и роли** — проверяются через имперсонацию под разных пользователей (из таблицы «Демо-пользователи»)
- **Каждый блок имперсонации закрывается шагом `Вернуться под себя`** — иначе следующие шаги пойдут от чужого пользователя и упрутся в ACL
- Имя в шаге имперсонации должно **буквально совпадать** с именем из таблицы «Демо-пользователи» — по нему идёт поиск пользователя при прогоне
- **Навигация** — через конкретные URL (`/record/<table>`, `/list/<table>`, `/portal/<page>`) или пункты меню
- **Бизнес-правила и клиентские скрипты** — покрываются шагами, которые вызывают их срабатывание
- **Виджеты** — показ размещения, взаимодействие с элементами
- **ALT-потоки** из UC — как отдельные подсценарии
- Невидимые FR (внутренние BR без UI-проявлений) — помечаются `Проверяется косвенно через шаг N` в таблице покрытия

### Шаг 5: Записать _demo_plan.md

Полностью записать в `<product>/<current_feature_path>/_demo_plan.md`.

JSON-файлы НЕ изменяются.

### Режим ultra

`--ultra` в аргументах — вызов из `/simplegen.ultra` (канон — `ultra-rules`). Отличия:

- **Шаг 0** пропустить — версию проверил оркестратор.
- **Пользователи.** Блок «Демо-пользователи» строить так, чтобы покрыть роли кейсов из таблицы «Тестовые пользователи» локального `_local/test_cases.md`, если он есть: из демо-пользователей берутся пользователи для тестов на стенде.
  - Для кейсов «без `<role>`» — демо-пользователь без этой роли (только базовые роли).
- **Права учётки прогона.** Выдачу роли `impersonator` (или любой роли) учётке прогона в демоданные не добавлять **никогда**: согласие на интервью не покрывает изменение прав учётки. Есть ли право, проверяет `test-author` по меню в браузере; права нет — кейсы под ролями уходят в SKIP, а в плане остаётся ручной шаг «выдать роль `impersonator`».
- **Системные свойства.** Шаги с `sys_property` — только ручными шагами: это конфигурация, а не демоданные.
- **Особые случаи.** В режиме ultra демо-план строится фоном во время финального ревью и `build`, по спеке, плану, кейсам и коду — стенд не нужен. Шаги вида «Загрузить SOP» — ручные, как обычно. Предупреждения особых случаев не выводить пользователю, а вернуть оркестратору для журнала.

### Нет спецификации

```markdown

```

### Нет активной фичи

```markdown

Сначала выберите или создайте фичу:

```

### Код ещё не сгенерирован

Если `<product>/domain/` не содержит изменений для текущей задачи:

```markdown
⚠️ Код для задачи ещё не сгенерирован. Демо-план будет построен по спецификации без анализа реализации.

Рекомендуется:
→ `/simplegen.code_generate` — сгенерировать код
→ `/simplegen.product_patch` — задеплоить
→ `/simplegen.demo_plan` — сформировать демо-план
```

### SOP ещё не задеплоен

```markdown
⚠️ SOP для текущей задачи не найден в каталоге задачи.

Демо-план будет создан, но для его воспроизведения необходим деплой:
→ `/simplegen.product_patch` — собрать и задеплоить
```

## Загрузка контекста

Перед работой обязательно:
1. **`demo-rules`** — канон демо-прогона (имперсонация, возврат под себя, отсутствие пароля у демо-пользователя)
2. **`_spec.md`** — полностью (UC, FR, модель данных, роли, UI)
3. **`_task_plan.md`** — полностью (фазы, задачи, файлы, трассировка)
4. **`<product>/domain/`** — реализованные сущности (таблицы, ACL, виджеты, скрипты, формы, навигация)
5. **`<product>/AGENTS.md`** — контекст продукта

## Примеры демо-планов (few-shot)

Ниже — реальные демо-планы, написанные разработчиками. Используй их как **образцы стиля, уровня детализации и формата** при генерации `_demo_plan.md`.

> **⚠️ Формулировки шагов имперсонации бери из канона, а не из примеров.** В примерах встречается «Имперсонироваться под пользователя X» без роли и без возврата — это исторический стиль. В генерируемом плане всегда `Имперсонироваться под <Имя> (<role_name>)` и парный шаг `Вернуться под себя`.

### Пример A — Демоданные с пользователями/ролями + виджеты + системные свойства

```text
Демоданные.

Создать записи в таблице cотрудник и выдать им соответствующие роли; (/record/employee):

User manager 3831
Выдать пользователю роль knowledge_agent.

Second User 3831
Указать в поле {manager} пользователя User manager.
Выдать пользователю роль knowledge_agent.

WTM Admin 3831
Выдать пользователю роль wtm_admin.

Admin 3831
Выдать пользователю все роли

Создать записи в таблице задачи с полями; (/record/task): 
- subject: Согласованная задача;
- subject: Очень важная задача;
- subject: Не важная задача;

Загрузить подготовленные файлы с добавлением новой функциональности; (/record/sys_vcs_retrieved_pack)

Демонстрация.

Продемонстрировать системные свойсва которые:
- опеределяет значение по умолчанию для списаеия впемени = 8 часов в сутки;
```
