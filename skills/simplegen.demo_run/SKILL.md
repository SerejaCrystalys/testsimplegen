## Назначение

> **⚡ BETA**: Автоматическое воспроизведение в браузере может вести себя непредсказуемо: элементы UI платформы могут не распознаваться, шаги — проваливаться из-за рендеринга или таймингов. Используйте результаты как вспомогательный инструмент, а не как окончательную верификацию.

Команда `/simplegen.demo_run` воспроизводит **блок «Демонстрация»** из `_demo_plan.md`:
- Проверяет предусловия: браузер, право имперсонации, наличие демоданных
- Выполняет пошаговое воспроизведение с проверкой ожидаемых результатов — **все демонстрируемые действия
  через интерфейс**, включая создание записей, кнопки и переходы состояний (`demo-rules`: «Демоданные и
  демонстрация — это разные вещи»)
- Переключается между демо-пользователями через имперсонацию и **всегда возвращается под себя**
- Ведёт структурированный лог в `_demo_log.md`
- Формирует итоговый отчёт в чат

> **Демоданные готовятся до запуска.** `/simplegen.demo_data_prepare` генерирует `_demo_data.json`, `/simplegen.demo_data_apply` создаёт записи на стенде. `demo_run` работает только с блоком «Демонстрация».

> **Как работать с браузером и имперсонацией — канон `demo-rules`.** Здесь описан только алгоритм прогона; селекторы, работа с браузером и процедура имперсонации не дублируются.

> **Примечание**: `<product>` в этом документе означает любой продукт, включая `sa/` с вендорскими правами.

## Синтаксис

```
/simplegen.demo_run              # весь сценарий демонстрации
/simplegen.demo_run 1-3          # только шаги 1-3
/simplegen.demo_run 5-           # с шага 5 до конца
/simplegen.demo_run --continue   # продолжить с шага, следующего за последним записанным в _demo_log.md
/simplegen.demo_run --present    # режим показа: видимое окно, темп для зрителя, баннер шагов
```

> **`--present`** — прогон для демонстрации людям (созвон, шаринг экрана): видимый браузер, паузы
> 3–4 с между шагами, экранный баннер с номером и названием шага и текущим пользователем, подсветка
> элементов перед кликом. Детали — `demo-rules`, раздел «Режим показа». Проверки и лог те же, что в
> обычном прогоне.

## Алгоритм работы

### Шаг 0: Проверить версию simplegen (⚠️ ОБЯЗАТЕЛЬНО)

Сравнить `version` (`.simplegen/state.json`) с выводом `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; CLI выше — `/simplegen.init`; совпадают — продолжить. Правило (канон) — `project-core-rule` (always-on).

### Шаг 1: Загрузить контекст

1. Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`)
2. Загрузить `<product>/<current_feature_path>/_demo_plan.md`
3. Если `_demo_plan.md` не найден — ошибка:
   ```
   ⚠️ Демо-план `_demo_plan.md` не найден.
   → `/simplegen.demo_plan` — сформировать демо-сценарий
   ```
4. Загрузить `_demo_data.json`, если есть — из него берутся `sys_id` демо-пользователей и записей
5. Загрузить `.env` — `SIMPLEONE_URL`, `SIMPLEONE_LOGIN`, `SIMPLEONE_PASSWORD`
6. Если `SIMPLEONE_URL` не задан — ошибка:
   ```
   ⚠️ Переменная SIMPLEONE_URL не задана.
   → Настройте .env (см. README)
   ```
7. Определить диапазон шагов из `$ARGUMENTS`. При `--continue` прочитать `_demo_log.md`, найти **последний записанный** шаг (любой статус: PASS / FAIL / SKIP) и начать со следующего

### Шаг 2: Проверить окружение (⚠️ ОБЯЗАТЕЛЬНО)

1. **Браузер.** Убедиться, что агенту доступны браузерные инструменты (открыть страницу, снять снимок, кликнуть). Если нет — остановиться:
   ```
   ⚠️ В этой IDE нет браузерного инструмента — прогнать демо автоматически нельзя.
   → Пройдите `_demo_plan.md` вручную как чек-лист
   ```
   Инструменты, которых нет в списке доступных, не выдумывать (`demo-rules`).
2. **Право имперсонации.** Если демо-план содержит шаги имперсонации — выполнить `simplegen demo whoami`. При `impersonate_access: false` остановиться:
   ```
   ❌ У учётной записи нет права имперсонации.
   → Выдайте роль `impersonator` пользователю из SIMPLEONE_LOGIN
   → Или проведите демо вручную по _demo_plan.md
   ```

### Шаг 3: Авторизоваться на стенде

Выполнить процедуру авторизации из `demo-rules` (селекторы `username-login-field`, `password-login-field`, `login-button`).

Если авторизация не удалась — остановить:
```
❌ Не удалось авторизоваться на стенде.
→ Проверьте SIMPLEONE_LOGIN / SIMPLEONE_PASSWORD в .env
→ Или авторизуйтесь вручную и перезапустите /simplegen.demo_run
```

Сразу после входа — снять возможную незакрытую имперсонацию от прошлого прогона (`demo-rules`, «Вернуться под себя»).

### Шаг 4: Проверить демоданные

Быстрая проверка (не полная — только критичные сущности), уже под авторизованной сессией:

1. Из блока «Демоданные» в `_demo_plan.md` и из `_demo_data.json` взять 1-2 ключевые сущности
2. Для демо-пользователей — `simplegen demo users --search "<имя>"`
3. Для записей — `browser_navigate` на список таблицы + `browser_find`
4. Если проверка провалилась — предупредить, но **не останавливать**:
   ```
   ⚠️ Предусловие: не найдены записи из блока «Демоданные».
   → `/simplegen.demo_data_prepare` — сгенерировать _demo_data.json
   → `/simplegen.demo_data_apply` — создать записи на стенде
   Продолжаем демонстрацию — ошибки будут зафиксированы в логе.
   ```

### Шаг 5: Инициализировать лог

1. Создать (или **дополнить** при `--continue`) `<product>/<current_feature_path>/_demo_log.md`
2. Записать заголовок:

```markdown
# Лог демонстрации: [Название фичи]

**Дата запуска**: [ISO timestamp]
**Стенд**: $SIMPLEONE_URL
**Демо-план**: `_demo_plan.md`
**Диапазон шагов**: [все / 1-3 / 5- / continue от N]
**Пользователь прогона**: [username из SIMPLEONE_LOGIN]

---
```

### Шаг 6: Выполнить блок «Демонстрация»

> При указании диапазона (например `1-3`) — выполнить только указанные шаги.
> При `--present` — перед каждым шагом обновить экранный баннер и держать темп для зрителя (`demo-rules`).

Для каждого нумерованного шага из секции «Демонстрация» в `_demo_plan.md`:

#### 6.1: Интерпретировать действие

| Паттерн в тексте                          | Действие                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------- |
| `Перейти на...` / `Открыть...` + URL      | `browser_navigate` на `$SIMPLEONE_URL` + путь                                         |
| `В меню навигатора выбрать...`            | `browser_snapshot` + `browser_click` по пунктам меню                                  |
| `Создать запись...` / `Заполнить форму...` | `browser_navigate` на `/record/<table>` → `browser_fill_form` → `browser_click` Save — **через интерфейс, не через API** |
| `Нажать кнопку "..."` / `Нажать ПКМ...`   | `browser_click` (для ПКМ — `button: "right"`)                                          |
| `Заполнить поле...` / `Указать в поле...` | `browser_type` (одно поле) или `browser_fill_form` (несколько)                        |
| `Перевести в состояние...`                | `browser_click` по кнопке перехода либо по контролу состояния и варианту, затем Save    |
| `Имперсонироваться под...`                | Процедура имперсонации из `demo-rules` (меню пользователя → Impersonate)               |
| `Вернуться под себя`                      | Кнопка «Back to me» в меню пользователя (`demo-rules`, Шаг 4)                          |
| `Продемонстрировать...`                   | `browser_snapshot` + `browser_take_screenshot` (фиксация текущего состояния)           |
| `Скопировать...` / `Вставить...`          | `browser_click` с `button: "right"` + `browser_click` по пункту контекстного меню      |

#### 6.2: Проверить ожидаемые результаты

Каждый вложенный подпункт (начинается с `- `) — это проверка. Таблица соответствий формулировок и способов проверки — в `demo-rules`, раздел «Проверки ожидаемых результатов». Зафиксировать результат: **PASS** / **FAIL** + детали.

#### 6.3: Записать результат шага в _demo_log.md

**Немедленно** после завершения каждого шага — **дописать** результат.

Формат записи для **успешного** шага:

```markdown
## Шаг N: [текст шага из демо-плана] — ✅ PASS

**Время**: [ISO timestamp]
**От пользователя**: [username] ([роль])
**Скриншот**: `[task_id]_step[N].png`

- [проверка 1] — ✅
- [проверка 2] — ✅
```

Формат записи для **провалившегося** шага:

```markdown
## Шаг N: [текст шага из демо-плана] — ❌ FAIL

**Время**: [ISO timestamp]
**От пользователя**: [username] ([роль])
**Скриншот**: `[task_id]_step[N].png`

- [проверка 1] — ✅
- [проверка 2] — ❌ Ожидалось: [что ожидалось]. Фактически: [что обнаружено]

**Детали ошибки**: [краткое описание — что пошло не так]
```

Формат записи для **пропущенного** шага:

```markdown
## Шаг N: [текст шага из демо-плана] — ⏭️ SKIP

**Время**: [ISO timestamp]
**Причина**: Зависит от шага M (FAIL)
```

> **Важно**: лог пишется **инкрементально** — после каждого шага, а не в конце. Если выполнение прервётся, лог будет содержать все завершённые шаги.
>
> **Поле «От пользователя» обязательно** — по логу должно быть однозначно видно, под кем выполнялся каждый шаг.

#### 6.4: Обработка ошибок в демонстрации

- При **FAIL** шага — записать в лог, сделать скриншот, перейти к следующему шагу
- При **критической ошибке** (страница не загрузилась, потеряна авторизация) — записать в лог, попытаться восстановить авторизацию; если не удалось — остановить
- При **зависимости от предыдущего FAIL** (например, запись не создана → нельзя открыть) — пометить **SKIP** с причиной
- При **FAIL внутри блока имперсонации** — всё равно выполнить возврат под себя перед следующим блоком

#### 6.5: Классифицировать каждый FAIL (⚠️ ВАЖНО)

| Категория | Признак | Куда |
| --------- | ------- | ---- |
| Дефект реализации | стенд не соответствует `_spec.md` (заголовок, поля, состояние, доступ) | «Расхождения со спецификацией» |
| Ошибка демо-плана | стенд соответствует `_spec.md`, неточен шаг: URL, имя пользователя, значение, несуществующая кнопка | «Замечания к демо-плану» |
| Помеха прогона | остатки прошлого прогона, нет демоданных, не отрисовалось, потеря сессии | только лог шага |

Формулировка с привязкой к источнику: «FR-07: ожидался заголовок “Подтверждение”, на стенде — “Подтвердите действие”».

**Ничего не править автоматически** — ни код, ни `_spec.md`, ни `_demo_plan.md`. Прогон только фиксирует.
Правку пользователь запускает явно: дефект → `/simplegen.code_generate` + `product_patch`; ошибка плана →
`/simplegen.demo_plan` или точечная правка названных им пунктов.

### Шаг 7: Завершить прогон

1. **Вернуться под себя**, если имперсонация активна (обязательно — даже при аварийном завершении)
2. Дописать итоги в `_demo_log.md`:

```markdown
---

## Итоги

**Завершено**: [ISO timestamp]
**Имперсонация снята**: да / нет

| Метрика            | Значение                                   |
| ------------------ | ------------------------------------------ |
| Всего шагов        | N                                          |
| PASS               | X                                          |
| FAIL               | Y                                          |
| SKIP               | Z                                          |
| Имперсонаций       | K (возвратов: K)                           |
| FR покрыто         | M (из таблицы Покрытие FR в _demo_plan.md) |

### Непройденные шаги

| #   | Действие               | Статус | Причина                |
| --- | ---------------------- | ------ | ---------------------- |
| 3   | Имперсонация под [Имя] | ❌ FAIL | Пользователь не найден |
| 4   | Проверить ACL          | ⏭️ SKIP | Зависит от шага 3      |

### Расхождения со спецификацией

| #   | Требование | Ожидалось | Фактически |
| --- | ---------- | --------- | ---------- |
| 2   | FR-07      | Заголовок «Подтверждение» | «Подтвердите действие» |

### Замечания к демо-плану

| #   | Что не так                 | Как должно быть |
| --- | -------------------------- | --------------- |
| 5   | Шаг ведёт на `/list/task`  | `/record/task`  |

### Рекомендации

- [Рекомендации по исправлению]
```

3. Вывести отчёт в чат вместе с обоими разделами. Разделы писать всегда; нет находок — «Расхождений не обнаружено»

## Правила воспроизведения

Полный канон — `demo-rules`. Ключевое:

- **Только реально доступные инструменты.** `browser_fill` и `browser_search` не существуют нигде.
- **Селекторы по `data-test`**, а не по хрупким ref, где это возможно.
- **`browser_wait_for`** вместо фиксированных пауз.
- **`browser_take_screenshot` с явным `filename`** вида `[task_id]_step[N].png`.
- **Лог после каждого шага**, не накапливать.
- **Имперсонация всегда закрывается возвратом под себя.**

### Стратегия при ошибках

| Ситуация                | Действие                                                           |
| ----------------------- | ------------------------------------------------------------------ |
| Элемент не найден       | `browser_find` / повторный `browser_snapshot`, затем ещё одна попытка |
| Страница не загрузилась | `browser_wait_for` (до 10 сек), при неудаче — FAIL, записать в лог  |
| Потеряна авторизация    | Повторить авторизацию (Шаг 3), продолжить                          |
| FAIL демонстрации       | Записать в лог, продолжить (если нет зависимости)                   |
| Зависимость от FAIL     | SKIP с причиной в логе                                             |
| Имперсонация не удалась | FAIL шага, зависимые шаги — SKIP, остаться под собой                |
| 4+ неудачных попытки    | Остановить, записать в лог, сообщить о блокере                      |

## Особые случаи

### Нет демо-плана

```markdown
⚠️ Демо-план `_demo_plan.md` не найден.

Сначала создайте демо-план:
→ `/simplegen.demo_plan`
```

### Нет активной фичи

```markdown
⚠️ Активная фича не установлена.

→ `/simplegen.context_set <task_id>`
→ `/simplegen.spec_create [описание]`
```

### Стенд недоступен

```markdown
❌ Стенд $SIMPLEONE_URL недоступен.

→ Проверьте URL в .env
→ Проверьте доступность стенда
```

### Требуется ручное действие

Если шаг требует действия, невозможного в браузере автоматически (загрузка файла на стенд, 2FA и т.д.):

```markdown
⚠️ Шаг N требует ручного действия:
[описание действия]

→ Выполните действие вручную
→ Затем продолжите: /simplegen.demo_run N+1
```

### Продолжение после прерывания

При `--continue` или диапазоне `N-`:

1. Прочитать `_demo_log.md`
2. Найти **последний записанный** шаг (любой статус: PASS / FAIL / SKIP)
3. Продолжить со следующего шага
4. Дописать результаты в тот же файл `_demo_log.md`
5. Перед первым шагом — снять незакрытую имперсонацию, если она осталась
