## Назначение

Команда `/simplegen.product_build` полностью пересобирает решение из DSL в **новую** сопку через CLI `simplegen build`, выгружает её в самодостаточный SOP-файл, затем откатывает сопку и переимпортирует SOP как retrieved pack — на стенде остаётся чистый самодостаточный пакет без лишних записей.

В отличие от `/simplegen.product_patch` (live-дозапись поверх стенда), `product_build` собирает с нуля и формирует финальный артефакт поставки.

`<product>` — любой продукт, включая `sa/`.

## Шаг 1: Проверка версии

`version` из `.simplegen/state.json` vs `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; выше — `/simplegen.init`; совпадают — продолжить. Правило (канон) — `project-core-rule` (always-on).

## Шаг 2: Контекст и pre-checks

1. Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`), затем `initial_commit_sha` из `<product>/<current_feature_path>/simplegen.json`.
2. Нет активной задачи → сообщить (`/simplegen.context_set` или `/simplegen.spec_create`).
3. Незакоммиченные изменения → предупредить и попросить закоммитить перед экспортом (пакет собирается из закоммиченной истории).

## Шаг 3: Превью

Выполнить `simplegen build <productName> --dry-run` и показать вывод **как есть**. Нужен список изменённых файлов — тот же вызов с `--verbose`. Dry-run считает тем же конвейером, что и сама сборка, в сеть не ходит и состояние не меняет.

В строке `Scope:` видно, сузился ли состав пакета. `excluded` — записи, пришедшие из целевой ветки (мердж master в рабочую ветку, ребейз): они в пакет не попадут, и это правильно. Если там оказалось что-то из **текущей** задачи — значит ветка отколота не от master: задать `SIMPLEGEN_TARGET_BRANCH` с именем родительской ветки и повторить превью.

Дождаться подтверждения: «Собираю пакет? (да/нет)»

## Шаг 4: Экспорт и цикл исправлений

Выполнить `simplegen build <productName> [--commit <ref>]`.

`--commit` — только если пользователь назвал коммиты: `X` — ровно коммит X, `X..Y` / `X..HEAD` — коммиты после X до Y, файлы на момент конца диапазона. Пакет соберётся только из них, а предыдущий пак задачи будет откачен — для поставки обычно нужен `build` без флага.

### Как определить исход

Исход определяется **наличием JSON в stdout**, а не кодом возврата: `process.exitCode = 1` CLI выставляет и при одних лишь предупреждениях.

| Исход | Как распознать |
| ----- | -------------- |
| Провал окружения | JSON не напечатан; `[error] …` содержит фрагмент из списка «Ошибки деплоя, которые не исправить правкой DSL» (`project-core-rule`) |
| Провал | JSON не напечатан; в stderr строка `[error] …` |
| Нечего собирать | JSON напечатан, `sopPath: null`, `recordCount: 0` |
| SOP не выгружен | JSON напечатан, `sopPath: null`, `recordCount` больше 0 |
| Успех с замечаниями | JSON напечатан, `sopPath` задан, `warnings[]` не пуст |
| Чистый успех | JSON напечатан, `sopPath` задан, `warnings[]` пуст |

⚠️ Провал сборки CLI отрабатывает сам: созданный локальный пакет откатывается, на стенде записей не остаётся (не удался и откат — это видно в логе сборки). Вручную ничего не чистить. Этим `build` отличается от `patch`, где отправленное до ошибки остаётся жить.

При **провале окружения**: показать сообщение и действие из списка `project-core-rule`, остановиться. `code-author` не запускать.

При **провале**:
1. Запустить `code-author`(fix) с текстом `[error] …` и самым свежим `build_logs/[<PRODUCT>]_<task_id>_<YYYY-MM-DD>_<HH-MM-SS>.log.json`: CLI пишет его сам, если упал на стенде.
2. Повторить экспорт. Не более 3 попыток; при неудаче — показать ошибку и лог, остановиться.

Если **нечего собирать**: SOP не создан. CLI к этому моменту уже откатил прежнюю сопку задачи (`last_patch.local_pack_id`, если она была), поэтому на стенде больше нет её прошлых патчей. Сообщить это пользователю. `code-author` не запускать.

Если **SOP не выгружен**: записи отправлены и применены на стенде в сопке `localPackId`, но нового SOP нет. Если задачу уже собирали, `[<PRODUCT>]_<task_id>.sop` в каталоге задачи остался от прежней сборки и с DSL не совпадает: не коммитить его. Причина — в `warnings[]` (`Failed to export SOP`). Показать предупреждения и предложить повторить `/simplegen.product_build`. `code-author` не запускать.

При **успехе с замечаниями**:
- Пакет собран. Не откатывать, цикл сборок не запускать.
- Один прогон `code-author`(fix) по замечаниям (критерии — в `code-author`), повторную сборку предложить пользователю. Предупреждения выгрузки, импорта и определения сопки (список — в `project-core-rule`) — не про DSL: только в отчёт, `code-author` по ним не запускать.
- Отчёт как при успехе + блок «⚠️ Замечания» с итогом разбора.
- `retrievedPackState: null` значит, что импорт не состоялся (`Failed to import SOP into retrieved pack`). SOP-файл есть, но записей задачи на стенде может не быть: сказать об этом и предложить повторить `/simplegen.product_build`.

При **чистом успехе**:
- CLI уже записал SOP в `sopPath` и сам заархивировал прежний в `build_logs/`. Ничего не копировать и не сохранять.
- Для отчёта взять из JSON `sopPath`, `recordCount`, `localPackId` (сопка, которую создал импорт) и `retrievedPackState.state`. Лог — самый свежий `build_logs/[<PRODUCT>]_<task_id>_<YYYY-MM-DD>_<HH-MM-SS>.log.json` (время UTC).

## Режим ultra

`--ultra` в аргументах — вызов из `/simplegen.ultra` (канон — `ultra-rules`). Согласие на сборку получено на интервью. Отличия:

- **Шаг 1** пропустить — версию проверил оркестратор.
- **Шаг 2.** Незакоммиченные изменения не обсуждать с пользователем: оркестратор коммитит до вызова. Дерево всё равно грязное → вернуть ошибку оркестратору.
- **Шаг 3.**
  - Dry-run выполнить, вывод вернуть оркестратору для журнала; подтверждения не ждать.
  - В `excluded` попали записи текущей задачи → `ULTRA_BLOCKED`, сборку не запускать.
- **Шаг 4, провал** — до 3 попыток:
  1. `code-author` (fix, `ultra:auto`).
  2. Оркестратор коммитит исправление (`fix: <task_id> — сборка, попытка N`, явный список файлов).
  3. Повтор `simplegen build`.

  Коммит обязателен: `build` собирает пакет только из закоммиченной истории, рабочее дерево не читает. Не вышло → вернуть провал оркестратору: это стоп-условие.
- **Данные стенда.** `build` откатывает пак patch и импортирует SOP: записи, вставленные паком задачи, создаются заново. Runtime-данные в таблицах задачи (демоданные, тестовые записи), созданные до сборки, могут пропасть — оркестратор учитывает это в порядке этапов.
- **Шаг 4, успех с замечаниями.**
  1. Один прогон `code-author` (fix, `ultra:auto`) по `warnings[]`.
  2. Есть правки → оркестратор коммитит → **одна** повторная сборка без вопроса.
  3. Оставшиеся замечания — флагами.
- **Итог** — вместо отчёта пользователю вернуть оркестратору:
  - исход;
  - путь SOP, размер, число записей;
  - новую сопку;
  - путь лога.

## Формат вывода

### Успешный экспорт

```markdown
# ✅ Пакет собран

## SOP

| Параметр | Значение |
|----------|----------|
| Файл | `[ITSM]_STR001234.sop` |
| Размер | 125 KB |
| Записей | 42 |

## Стенд

| Параметр | Значение |
|----------|----------|
| URL | https://dev.example.com |
| Сопка (после импорта) | `123456789012345678` |
| Retrieved pack | `234567890123456789` (`committed`) |
| Статус | ✅ Самодостаточный пакет применён |

## Лог API

| Параметр | Значение |
|----------|----------|
| Файл | `build_logs/[ITSM]_STR001234_2025-12-10_14-30-05.log.json` |

## Следующий шаг

→ Передать `[ITSM]_STR001234.sop` на поставку
→ `/simplegen.product_patch` — продолжить live-итерации
→ `/simplegen.product_rollback` — откатить (если нужно)
```

```markdown
# ❌ Пакет не собран

`build_logs/[ITSM]_STR001234_<YYYY-MM-DD>_<HH-MM-SS>.log.json` (если CLI упал до обращения к стенду, лога нет)

## Следующий шаг

→ Исправьте ошибку (ошибка окружения или стенда — действие из списка в `project-core-rule`)
→ `/simplegen.code_generate` — перегенерировать
→ `/simplegen.product_build` — повторить экспорт
```
