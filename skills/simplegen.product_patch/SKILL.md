## Назначение

Команда `/simplegen.product_patch` берёт дифф `last_patch.commit_sha..HEAD` (включая рабочее дерево) и **дозаписывает** изменённые записи в единую сопку (local pack) на стенде через CLI `simplegen patch`.

- Работает с live-стендом: записи применяются сразу.
- Не выполняет откат изменений.
- Все изменения накладываются поверх текущего состояния стенда.
- Все сборки идут в **одну сопку**, созданную при первом вызове `/simplegen.product_patch` (хранится в `last_patch.local_pack_id`).

Для полной самодостаточной пересборки с нуля используйте `/simplegen.product_build`.

`<product>` — любой продукт, включая `sa/`.

## Шаг 1: Проверка версии

`version` из `.simplegen/state.json` vs `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; выше — `/simplegen.init`; совпадают — продолжить. Правило (канон) — `project-core-rule` (always-on).

## Шаг 2: Контекст и pre-checks

1. Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`), затем `last_patch` из `<product>/<current_feature_path>/simplegen.json`.
2. Нет активной задачи → сообщить (`/simplegen.context_set`).
3. Первый вызов (нет `last_patch`) — это нормально: сопка будет создана автоматически от `initial_commit_sha`.
4. Незакоммиченные изменения дозаписываются (учитывается рабочее дерево), но рекомендуется закоммитить, чтобы дифф сдвигался корректно.

## Шаг 3: Превью

Выполнить `simplegen patch <productName> --dry-run` и показать вывод **как есть**. Нужен список изменённых файлов — тот же вызов с `--verbose`. Dry-run считает тем же конвейером, что и сам патч, в сеть не ходит и `simplegen.json` не двигает.

В строке `Scope:` видно, сузился ли состав пакета. `excluded` — записи, пришедшие из целевой ветки (мердж master в рабочую ветку, ребейз): они в пакет не попадут, и это правильно. Если там оказалось что-то из **текущей** задачи — значит ветка отколота не от master: задать `SIMPLEGEN_TARGET_BRANCH` с именем родительской ветки и повторить превью.

Дождаться подтверждения: «Запускаю сборку? (да/нет)»

## Шаг 4: Сборка и цикл исправлений

Выполнить `simplegen patch <productName> [--commit <ref>]`.

`--commit` — только если пользователь назвал коммиты: `X` — ровно коммит X, `X..Y` / `X..HEAD` — коммиты после X до Y. С ним рабочее дерево не участвует, файлы читаются на момент конца диапазона, `last_patch.commit_sha` встаёт на конец диапазона. Без флага — дифф от `last_patch.commit_sha` до рабочего дерева.

### Как определить исход (⚠️)

Исход определяется **наличием JSON в stdout**, а не кодом возврата: `process.exitCode = 1` CLI выставляет и при одних лишь предупреждениях.

| Исход | Как распознать |
| ----- | -------------- |
| Провал окружения | JSON не напечатан; `[error] …` содержит фрагмент из списка «Ошибки деплоя, которые не исправить правкой DSL» (`project-core-rule`) |
| Провал | JSON не напечатан; в stderr строка `[error] …` |
| Успех с замечаниями | JSON напечатан, `warnings[]` не пуст |
| Чистый успех | JSON напечатан, `warnings[]` пуст |

⚠️ Провал патча **частичный по своей природе**: записи, отправленные до ошибки, остаются на стенде — это уже применённые правки, их не откатывают. `last_patch.commit_sha` при этом намеренно не сдвигается, поэтому повтор отправит то же окно целиком: уже уехавшие записи обновятся по сохранённым `sys_id`, а не задублируются. Ничего не откатывать и не чистить вручную.

При **провале окружения**: показать сообщение и действие из списка `project-core-rule`, остановиться. `code-author` не запускать.

При **провале**:
1. Запустить `code-author`(fix) с текстом `[error] …` и самым свежим `build_logs/…_patch.log.json`: CLI пишет его сам, в том числе при ошибке отправки.
2. Повторить сборку. Не более 3 попыток; при неудаче — показать ошибку и лог, остановиться.

При **успехе с замечаниями**:
- Деплой состоялся. Не откатывать, цикл сборок не запускать.
- Один прогон `code-author`(fix) по замечаниям (критерии — в `code-author`), повторную сборку предложить пользователю. Предупреждения стенда из `project-core-rule` — только в отчёт.
- Отчёт как при успехе + блок «⚠️ Замечания» с итогом разбора.

При **чистом успехе**:
- `last_patch.commit_sha` сдвигается на текущий HEAD автоматически (CLI).
- Записи остаются на стенде; откат не выполняется.
- Лог CLI пишет сам: `build_logs/[<PRODUCT>]_<task_id>_<YYYY-MM-DD>_<HH-MM-SS>_patch.log.json` (время UTC). Ничего не сохранять: в отчёт взять самый свежий такой файл.

## Режим ultra

`--ultra` в аргументах — вызов из `/simplegen.ultra` (канон — `ultra-rules`). Согласие на деплой получено на интервью. Отличия:

- **Шаг 1** пропустить — версию проверил оркестратор.
- **`--commit <диапазон>`** из аргументов передавать и в dry-run, и в `simplegen patch`. С ним CLI деплоит только закоммиченное, рабочая папка не участвует: незакоммиченный код следующей фазы на стенд не попадёт.
- **`code-author` (fix)** получает строку оркестратора `Чужая работа: <файлы>` из аргументов. В коммит исправления — только файлы из его отчёта, `_task_plan.md` — никогда. `ULTRA_FOREIGN` → вернуть оркестратору (склейка по правилу очерёдности `/simplegen.ultra`), затем повторить попытку.
- **Шаг 3.**
  - Dry-run выполнить, вывод вернуть оркестратору для журнала; подтверждения не ждать.
  - В `excluded` попали записи текущей задачи (ветка отколота не от целевой) → `ULTRA_BLOCKED`, патч не запускать.
- **Write-back перед исправлением.** После каждой попытки `simplegen patch` (и при провале: CLI дописывает `sys_id` уже созданных записей), до `code-author` (fix), оркестратор коммитит write-back: `chore: <task_id> — sys_id write-back`, только файлы, которые дописал CLI: файлы диапазона попытки, изменённые после неё (код фаз пула в диапазон не входит). Иначе исправление, удалившее такую запись, сотрёт её единственный `sys_id`, и повтор пропустит удаление (Известные ограничения, п. 2).
- **Шаг 4, провал** — до 3 попыток:
  1. `code-author` (fix, `ultra:auto`).
  2. Оркестратор коммитит исправление (`fix: <task_id> — деплой, попытка N`, явный список файлов): так правка попадает в дифф ревью и в историю.
  3. Повтор `simplegen patch`. С `--commit` — то же начало диапазона и новый конец: `--commit <начало>..HEAD`.
  4. Исправление удалило запись, которую создала упавшая попытка (файл или `export const` из коммита write-back перед ним) → после успешного повтора ещё `simplegen patch --commit <этот коммит write-back>..HEAD`. От начала диапазона такой записи нет ни на одном конце, повтор её удаление не видит. Без `--commit` — флаг «запись осталась на стенде».

  Не вышло → вернуть провал оркестратору: это стоп-условие.
- **Шаг 4, успех с замечаниями.**
  1. Один прогон `code-author` (fix, `ultra:auto`) по `warnings[]`.
  2. Есть правки → оркестратор коммитит → **один** повторный `simplegen patch` без вопроса. С `--commit` — `--commit <конец прошлого диапазона>..HEAD`: write-back первой попытки уже закоммичен (п. «Write-back перед исправлением»), `sys_id` удалённых записей CLI найдёт в истории.
  3. Оставшиеся замечания — флагами.
- **Итог** — вместо отчёта пользователю вернуть оркестратору:
  - исход;
  - сопку;
  - число записей;
  - HEAD;
  - путь лога;
  - файлы write-back `sys_id` последней попытки (прошлые уже закоммичены) — отдельно от файлов исправлений `code-author`.

## Формат вывода

### Успешный деплой

```markdown
# ✅ Деплой успешен

## Результат

| Параметр   | Значение |
| ---------- | -------- |
| Сопка      | `123456789012345678` |
| Записей    | 7 |
| HEAD       | `<headSha>` |
| Стенд      | ✅ Применён live |

## Лог API

| Параметр | Значение |
|----------|----------|
| Файл | `build_logs/[ITSM]_STR001234_2025-12-10_14-30-05_patch.log.json` |

## Следующий шаг

→ Продолжайте итерацию: правьте код и снова `/simplegen.product_patch`
→ `/simplegen.product_build` — собрать самодостаточный пакет для поставки
→ `/simplegen.product_rollback` — откатить сопку (если нужно)
```

### Нечего дозаписывать

```markdown
⚠️ Дифф пуст — изменений с последней сборки нет.

→ Внесите правки в `<product>/domain/` и закоммитьте
→ `/simplegen.product_build` — если нужна полная пересборка
```

### Ошибка деплоя

```markdown
# ❌ Деплой не удался

## Ошибка

```
[текст ошибки от SimpleOne]
```

## Лог

`build_logs/[ITSM]_STR001234_<YYYY-MM-DD>_<HH-MM-SS>_patch.log.json` (если CLI упал до отправки записей, лога нет)

## Следующий шаг

→ Исправьте ошибку (ошибка окружения или стенда — действие из списка в `project-core-rule`)
→ `/simplegen.product_patch` — повторить деплой
```

## Известные ограничения

1. **Накопление в одной сопке**: все итерации ложатся в одну сопку поверх текущего состояния стенда — она копит историю правок и не даёт «чистого» самодостаточного пакета. Для чистого состояния с нуля — `/simplegen.product_build`.
2. **Удаления требуют разрешимого `sys_id`**: удаление DSL-записи применяется на стенде (HTTP DELETE), но только если её `sys_id` разрешается из baseline. Если write-back `sys_id` ещё не закоммичен — удаление пропускается с предупреждением; закоммитьте write-back (или сделайте `/simplegen.product_build`) и повторите.
3. **Без отката при ошибке**: уже отправленные записи остаются на стенде live. Откат — `/simplegen.product_rollback`.
