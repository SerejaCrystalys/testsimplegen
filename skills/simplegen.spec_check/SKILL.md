## Назначение

On-demand ревью спецификации активной задачи: один прогон `spec-reviewer`, затем интеграция ответов пользователя через `spec-author` (fix). `_spec.md` — живой документ и единственный источник правды по требованиям.

По желанию команда **сверяет покрытие критериев приёмки**: вставьте критерии из постановки в аргументы — агент покажет, какой критерий каким FR/UC закрыт и что осталось за бортом за итерации уточнений. Критерии нигде не сохраняются, таблица выводится только в чат:

```
/simplegen.spec_check
Критерии приёмки:
- …
```

`<product>` — любой продукт, включая `sa/`.

## Шаг 1: Проверка версии

`version` из `.simplegen/state.json` vs `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; выше — `/simplegen.init`; совпадают — продолжить.

## Шаг 2: Ревью

Прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`). Нет активной задачи — сообщить (`/simplegen.context_set` или `/simplegen.spec_create`). Запустить субагента `spec-reviewer` (путь продукта + `current_feature_path`).

Критерии приёмки переданы в аргументах → вывести **первой** таблицу покрытия (из отчёта ревьюера), даже если других замечаний нет:

```markdown
| Критерий | FR / UC    | Статус       |
| -------- | ---------- | ------------ |
| AC-1     | FR-1, UC-1 | покрыт       |
| AC-2     | —          | ⚠️ не покрыт  |
| AC-3     | FR-4       | ⚠️ расхождение — требование изменено на … |
```

Затем:

- `VERDICT: PASS` → «замечаний нет», предложить `/simplegen.spec_plan`.
- Иначе → показать вопросы пользователю (формат `spec-reviewer`).

Критерии не переданы — сверку пропустить и ничего об этом не спрашивать: это опциональная часть команды.

## Шаг 3: Ответы и интеграция

Получив ответы, запустить субагента `spec-author` в режиме **fix** с ответами/ISSUES. Он точечно обновляет `_spec.md`; при наличии критериев пересчитывает покрытие для вывода в чат. В файлы задачи ни критерии, ни таблица покрытия не пишутся. При наличии `_task_plan.md` — дозаписывает `changelog.md` и предупреждает о необходимости `/simplegen.spec_plan`. JSON не меняется.

Если в ответах пользователя есть решения уровня реализации («сделаем через ACL», «поставим read only»), они в спеку не попадают — `spec-author` возвращает их отдельным блоком «Для таск-плана», передать его пользователю.
