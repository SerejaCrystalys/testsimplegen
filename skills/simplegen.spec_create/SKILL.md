## Назначение

Оркестратор создания спецификации: генерирует `_spec.md` через субагента `spec-author`, затем прогоняет цикл ревью `spec-reviewer` → `spec-author` (fix) до чистого результата.

Спека — артефакт **аналитика**: UC, FR, бизнес-модель данных, доступы, UI. Платформенные атрибуты и выбор механизма реализации в неё не попадают — они фиксируются в `_task_plan.md` (`/simplegen.spec_plan`).

Критерии приёмки — **вход** команды, а не раздел спеки: они раскрываются в FR и UC и нигде в задаче не дублируются. Сомневаетесь в их качестве — прогоните сначала `/simplegen.spec_assess` (опционально, ничего не создаёт).

`<product>` — любой продукт, включая `sa/`. Определяется по каталогу верхнего уровня с `AGENTS.md` (один продукт — авто; несколько — спросить).

## Шаг 1: Проверка версии

1. `version` из `.simplegen/state.json` vs `simplegen --version`.
2. CLI ниже — `⚠️ обновите: npm update @simplegen/simplegen`; CLI выше — `⚠️ выполните /simplegen.init`; совпадают — продолжить.

## Шаг 2: Генерация

Запусти субагента `spec-author` в режиме **create**, передав: `$ARGUMENTS` (task_id + бизнес-описание + критерии приёмки), путь продукта. Субагент создаёт каталог задачи, `_spec.md`, `changelog.md`, `simplegen.json` и выставляет активную фичу командой `simplegen context <product> <task_id>`.

Если `spec-author` вернул запрос на уточнение (мало данных / не указан ID / задача существует) — передать вопрос пользователю и не продолжать до ответа.

## Шаг 3: Цикл ревью → фикс

Повторять до `VERDICT: PASS`, но **не более 3 итераций**:

1. Запусти субагента `spec-reviewer` (путь продукта + `current_feature_path`). Он анализирует `_spec.md` и возвращает отчёт + `VERDICT`.
2. `VERDICT: PASS` → выйти из цикла.
3. `VERDICT: FAIL` с `ISSUES`:
   - Есть `NEEDS_USER_INPUT` → показать вопросы пользователю, дождаться ответов, затем запустить `spec-author` (fix) с ответами.
   - Только `AUTO` → запустить `spec-author` (fix) с этими ISSUES без участия пользователя.
4. Условия досрочной остановки: тот же набор ISSUES повторился дважды (нет прогресса) → остановиться и показать пользователю; `spec-author` пометил `NEEDS_USER_INPUT` → пауза + вопрос.

После 3 итераций без PASS — остановиться, показать остаточные ISSUES и спросить пользователя, продолжать ли уточнение или принять как есть.

## Шаг 4: Итог

Вывести результат `spec-author` (создана задача) и финальный статус ревью.

## Режим ultra

`--ultra` в аргументах — вызов из `/simplegen.ultra` после интервью (канон — `ultra-rules`). В аргументах — блок `ULTRA_ANSWERS`, исходное описание и критерии AC-N. Субагентам — `Режим: ultra:auto`. `spec-author` (fix) и `spec-reviewer` на **каждой** итерации получают критерии: без них покрытие не проверяется. Критерий, переставший покрываться из-за ответа интервью, — флаг. Отличия:

- **Только своя спека** (`ultra.spec_owner = ultra`). Готовую спеку (`analyst`) прогон не трогает, и команда для неё не вызывается.
- **Шаг 1** пропустить — версию проверил оркестратор.
- **Шаг 2.** Каталог задачи создан на разведке (есть `_local/ultra.json`) → вместо create запустить `spec-author` (fix) с `ULTRA_ANSWERS`. Каталога нет → create как обычно.
- **Шаг 3.**
  - `NEEDS_USER_INPUT` не показывать: `spec-author` (fix) принимает рекомендуемый вариант и возвращает `ULTRA_ASSUMPTIONS`.
  - Нет PASS после 3 итераций или ISSUES повторились → остаточные ISSUES вернуть как флаги и не спрашивать.
- **Шаг 4.** Вместо итога для пользователя вернуть оркестратору:
  - финальный `VERDICT`;
  - число итераций;
  - все `ULTRA_ASSUMPTIONS`;
  - флаги;
  - раздел «Для таск-плана».
