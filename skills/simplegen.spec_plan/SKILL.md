## Назначение

Оркестратор построения плана: запускает `plan-author`, затем цикл ревью `plan-reviewer` → `plan-author`(fix) до чистого результата.

План — артефакт **инженера**: помимо фаз и задач он содержит раздел **«Предварительное техническое решение»**, где бизнес-требования спеки переведены в платформенные механизмы (нередактируемость через ACL или чекбокс, поведение ссылок при удалении, отбор записей, места UI-действий). Спека этих деталей больше не содержит — её приёмщик аналитик.

`<product>` — любой продукт, включая `sa/`.

## Шаг 1: Проверка версии

1. `version` из `.simplegen/state.json` vs `simplegen --version`.
2. CLI ниже — `⚠️ обновите: npm update @simplegen/simplegen`; CLI выше — `⚠️ выполните /simplegen.init`; совпадают — продолжить.

## Шаг 2: Определить режим

- `$ARGUMENTS` содержит описание дефекта (STR, ожидаемое/фактическое) → режим **Defect**: запустить `plan-author` с описанием дефекта.
- Иначе → стандартный: прочитать активную фичу (`SIMPLEGEN_ACTIVE_FEATURE` в `.env`). Нет активной задачи — сообщить (`/simplegen.spec_create`). Нет `_spec.md` → сообщить.

**Merge прогресса.** Если `_task_plan.md` уже существует — `plan-author` не собирает план с нуля, а пересобирает состав из актуальной `_spec.md` и **переносит прогресс** (`- [x]`) на совпавшие задачи. Изменённые/удалённые задачи он сбрасывает/выносит с пометкой (детали — в `plan-author`). Первый запуск (плана нет) — обычная генерация.

## Шаг 3: Построение и цикл ревью

Повторять до `VERDICT: PASS`, не более 3 итераций:

1. Запустить `plan-author` (путь продукта + `current_feature_path`, режим create/fix + ISSUES при fix).
2. Запустить `plan-reviewer`. `VERDICT: PASS` → выйти из цикла.
3. `VERDICT: FAIL`:
   - Есть `NEEDS_USER_INPUT` → показать вопросы, дождаться ответов, передать в `plan-author`(fix).
   - Только `AUTO` → `plan-author`(fix) без паузы.
4. Те же ISSUES дважды → остановиться, эскалировать.

После 3 итераций без PASS — показать остаточные ISSUES, спросить пользователя.

## Шаг 4: Итог

Вывести отчёт `plan-author` и явно предложить инженеру проверить раздел «Предварительное техническое решение» до генерации кода: именно там зафиксировано, каким механизмом реализуется каждое бизнес-требование.

## Режим ultra

`--ultra` в аргументах — вызов из `/simplegen.ultra` (канон — `ultra-rules`). Субагентам — `Режим: ultra:auto`.

**Кто выполняет.** Шаги 2–3 ведёт сам оркестратор `/simplegen.ultra` по этому файлу, а не через вызов команды: пока идёт цикл плана, параллельно генерируется код готовых фаз (Шаг 4 оркестратора). Субагенты цикла — фоновые. После каждого `plan-reviewer` оркестратор читает его `PHASE_VERDICTS`.

Отличия:

- **Шаг 1** пропустить — версию проверил оркестратор.
- **Шаг 2.** План-черновик с разведки уже есть → обычный merge. `plan-author` получает:
  - тех. ответы интервью (`ULTRA_ANSWERS`);
  - раздел «Для таск-плана» журнала;
  - `spec_owner`;
  - список замороженных фаз.
- **Шаг 3.**
  - `NEEDS_USER_INPUT` не показывать: `plan-author` (fix) принимает решение по «Каталогу решений» и возвращает `ULTRA_ASSUMPTIONS`.
  - `AUTO` вида «вернуть на `/simplegen.spec_check`» (деталь реализации в спеке):
    - своя спека (`spec_owner = ultra`) → `spec-author` (fix, `ultra:auto`) с критериями AC-N из постановки выносит деталь из спеки, затем повторить `plan-author` в той же итерации;
    - спека аналитика (`spec_owner = analyst`) → спеку не трогать. `plan-reviewer` выносит такие замечания в блок `SPEC_REMARKS`, а не в ISSUES; оркестратор переносит их в журнал, «Замечания к спецификации». Деталь реализации `plan-author` учитывает в техническом решении.
  - **Цикл останавливают только 🔴.** Первый шаг — `plan-author` (fix) по ответам интервью и `AUTO` разведки, ревью разведки не повторяется. После `plan-reviewer`: ISSUES без 🔴 → последний `plan-author` (fix) по ним, цикл окончен без нового ревью. Не более 3 ревью: после третьего FAIL — последний `plan-author` (fix) без ревью, его ISSUES — в итог как «исправлено без перепроверки», оставшиеся 🔴 — флаги. ISSUES повторились → так же. Не спрашивать.
  - **`PHASES_TOUCHED`** из отчёта `plan-author` (fix) оркестратор учитывает при заморозке: фаза с `PASS` в последних `PHASE_VERDICTS`, которую автор с тех пор не трогал, готова к коду без нового ревью.
  - **Замороженные фазы** — начатые и готовые к старту фазы (Шаг 4 п. 3 `/simplegen.ultra`). Их список на каждой итерации получают `plan-author` (fix) и `plan-reviewer`: код этих фаз генерируется или стартует без повторной проверки.
- **Шаг 4.** Не предлагать инженеру проверить тех. решение: его утвердили на интервью. Итог для журнала:
  - финальный `VERDICT` и последние `PHASE_VERDICTS`;
  - число итераций;
  - `ULTRA_ASSUMPTIONS`;
  - флаги;
  - при спеке аналитика — замечания к ней, не внесённые в спеку.
