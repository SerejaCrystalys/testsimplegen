## Назначение

> **⚡ BETA**: режим в бета-тестировании. Проверяйте MR, допущения и флаги вручную; правила режима ещё меняются.

Оркестратор поэтапных команд. Делает за один запуск всё, что делают `spec_create` → `spec_plan` → `diagrams_build` → `code_generate` → `product_patch` → `product_build` → `product_verify` → `demo_*`. Добавляет тесты на стенде и merge request. В MR едут те же артефакты, что получились бы поэтапно, кроме документации модулей: `docs/` прогон не пишет, её обновляют отдельно через `/simplegen.docs_build`. Журнал прогона и описание MR — локальные, в ветку не коммитятся.

**Тесты — только для локальной проверки.** Тест-кейсы, отчёт и скриншоты лежат в `<product>/tasks/<task_id>/_local/`, Playwright — в `.simplegen/e2e/`. Оба каталога игнорирует git, в MR они не попадают. В описании MR — только итоги проверки. Собственный e2e-фреймворк продукта, если он есть, прогон не трогает.

**Вызов — это полный прогон.** `/simplegen.ultra` всегда проходит все этапы, от предпроверки до MR. Сузить его до «расследования», «только спеки» или «только решения» по своему усмотрению нельзя, предпроверку и интервью пропускать нельзя. Если человек сам просит меньше, это вопрос на интервью, а не молчаливое решение агента.

**Все вопросы — в начале.** После интервью и ответа «Поехали» прогон идёт без остановок. Вопрос, всплывший позже, решается рекомендуемым вариантом и попадает в MR блоком «Проверить допущения». Канон режима — `ultra-rules`: подрежимы, форматы блоков, стоп-условия, состояние, журнал, безопасность.

**Готовую спеку не трогать.** Если спека была до ultra, прогон её не правит совсем: ни текст, ни `changelog.md`, ни раздел «Диаграммы». Уточнения записываются в план, в раздел «Уточнения к спецификации», замечания к спеке — в журнал и MR, для аналитика.

**Код не ждёт.** Фаза уходит в генерацию, как только её участок плана прошёл ревью. Независимые фазы пишутся одновременно (пул до 3), закоммиченное деплоится очередью: одна фаза или несколько сразу, кто успел. Тестов на фазах нет: все тесты — в конце, на `patch`-стенде, до `build`. Тесты изолированы от демоданных: свои данные им создают фикстуры e2e-фреймворка продукта. Всё, что стенда не требует, — фоном: артефакты по спеке аналитика уже во время интервью, демо-план и черновик MR — во время финала.

`<product>` — любой продукт, включая `sa/` (при вендорских правах).

## Карта этапов

| # | Этап (`stage`) | Что происходит | Коммиты |
| - | -------------- | -------------- | ------- |
| 0 | `preflight` | Версия, git, стенд, инструменты, режим деплоя | — |
| 1 | `recon` | Черновики спеки и плана, сбор всех вопросов | — |
| 2 | `interview` | Единственная остановка: вопросы, тех. решение, «Поехали»; при спеке аналитика фоном — диаграммы спеки, черновик кейсов, документация | — |
| 3 | `spec` | Своя спека — правки с ответами и ревью; готовая спека — этап пропускается | `spec: …` |
| 4 | `artifacts` | Цикл плана; готовые фазы сразу уходят в код; тест-кейсы, документация, тексты интерфейса, диаграммы — фоном | `plan:`, `docs:` |
| 5 | `pipeline` | Пул фаз по графу зависимостей; деплой очередью, ревью по пачкам. Тестов нет | `feat:`, `fix:` |
| 6 | `review` | Финальное ревью всего диффа: стыки фаз | `fix: … ревью` |
| 7 | `final` | Все тесты на `patch`-стенде → дефекты через `patch` → `build` → `verify` ∥ проверка после сборки; демо-план, демоданные (файлом) и черновик MR — фоном | `fix:`, `build:`, `docs: demo` |
| 8 | `mr` | Описание MR, push, merge request | `docs: ultra …` |

Почему тесты идут до `build`: дефект на `patch`-стенде чинится обычным `patch`, без пересборки. `simplegen build` откатывает пак patch и импортирует собранный SOP: записи пака задачи (таблицы, колонки, роли) удаляются и создаются заново, поэтому runtime-данные в таблицах задачи могут пропасть. После сборки — короткая проверка: тесты заново создают свои данные фикстурами.

**Демоданные и тесты изолированы.** Тесты на демоданные не опираются вообще: свои данные каждый кейс создаёт сам — фикстурами e2e-фреймворка продукта. Демоданные прогон только генерирует (`_demo_plan.md`, `_demo_data.json`) и оставляет в MR; на стенд их не применяет.

## Правила оркестратора

**Субагенты и команды.**
- Субагентам — пути (продукт, `tasks/<task_id>`), строка режима (`Режим: ultra:collect` / `Режим: ultra:auto`), блок `ULTRA_ANSWERS` по формату `ultra-rules` и исходная постановка из журнала, если агент работает со спекой. Агентам спеки и плана — ещё `ultra.spec_owner` («спека аналитика» или «своя»). Есть ссылки на Figma в постановке или спеке → передавать их и `ultra.options.figma` всем, кто описывает или пишет интерфейс: `spec-author`, `spec-reviewer`, `plan-author`, `code-author`, ревьюеру с фокусом `интерфейс`, `test-author` — при любой спеке. При `figma = mcp` — разбирать макет через Figma MCP; при `screenshots` — по скриншотам и ответам интервью, без вопросов. Пересказ артефактов не передавать: агенты читают файлы сами.
- Параллельные вызовы — одним сообщением. Агенты, запущенные одновременно, не читают файлы, которые пишет другой из них. Два агента, создающих задачу, параллельно не запускаются: `simplegen context` переключает активную фичу глобально.
- Команды вызываются с `--ultra` первым словом аргументов (`/simplegen.code_generate --ultra 2`). Вызывать инструментом Skill; в IDE без него — прочитать файл команды из каталога команд IDE и выполнить его шаги. Отличия режима — в разделе «Режим ultra» каждой команды.
- Фоновые субагенты — там, где шаг это говорит. IDE без фоновых субагентов: те же шаги по очереди, без перекрытия.
- При `ultra.options.e2e = product` тесты пишутся и запускаются e2e-фреймворком продукта (`test-author`, «Фреймворк продукта»): `codify` не нужен, `rerun` — раннером фреймворка, данные кейсов — его фикстуры. Иначе:
- `test-author` в режимах `codify` и `rerun` вызывается только при `ultra.options.playwright = true` и готовом Playwright: он был установлен до прогона или `ultra.background.scaffold = done`. Иначе шаг пропускается без флага.

**Состояние.** `ultra.stage` выставлять в начале этапа; после этапа — `ultra.done += <этап>`. Схема — в `ultra-rules`.

**Наборы путей** — по ним собираются коммиты и проверяется дерево:

| Набор | Пути | Коммитится |
| ----- | ---- | ---------- |
| Код | `<product>/domain/`; `_task_plan.md` — только при `ultra.plan_loop = done` (пока цикл плана идёт, план коммитит лишь `plan:`) | Да |
| Метаданные задачи | `simplegen.json` задачи (`initial_commit_sha`, `last_patch` от CLI, `module`) | Да — вместе с коммитом, после которого они изменились: write-back, `build:`, `plan:` |
| Состояние прогона | `_local/ultra.json` | **Никогда**: локальный, в `.gitignore` |
| Журнал | `_local/_ultra_log.md` | **Никогда**: локальный, в `.gitignore` |
| Артефакты этапа | Перечислены в шаге этапа | Да |
| Локальные тесты и журнал | `<product>/tasks/<task_id>/_local/`, `.simplegen/e2e/`, `.playwright-mcp/` | **Никогда**: каталоги в `.gitignore` |

Локальные тесты в `git status` не видны и точке фиксации не мешают.

**Коммиты.**
- Коммитит только оркестратор, субагенты — никогда.
- Каждый коммит — явный список файлов из наборов: `git add -- <пути>`. Удалённые файлы добавляются тем же способом. Коммит фазы или исправления берёт только файлы своей работы — по отчёту `code-author` и целевым файлам задач плана, — а не всё изменённое в `domain/`: там может лежать незакоммиченный код следующей фазы. Файл из отчёта исправления оказался среди файлов фазы пула (в `generating` — её целевых по плану, в `written` — `phases.N.files`) → его не коммитить: склейка по правилу очерёдности.
- Список фильтруется до существующих путей и удалений, известных git (`git ls-files --deleted`). Пусто — коммит пропустить.
- Сообщение — файлом: `F="$(git rev-parse --git-path ULTRA_MSG)"`, затем `git commit -F "$F"`. Путь внутри каталога git: работает и в обычном клоне, и в worktree, и в коммит не попадает.

**Точка фиксации** — перед **каждым** `patch`, `build` и `verify`:
1. Фоновый артефакт закончил (`background.<имя> = done`) → его коммит по Шагу 4 п. 7, статус `committed`.
2. Изменён `simplegen.json` задачи и не вошёл в коммит своей работы → коммит `chore: <task_id> — task metadata`. Состояние прогона (`_local/ultra.json`) не коммитится.
3. Ожидаемые незакоммиченные файлы — их не коммитить и из-за них не останавливаться:
   - файлы работающих фоновых агентов: диаграммы, тексты интерфейса, раздел «Диаграммы» в `_task_plan.md` или своей `_spec.md`;
   - `_task_plan.md`, а при своей спеке — `_spec.md` и `changelog.md` (их правит `spec-author` цикла плана), пока `plan_loop = running`: они уходят в `plan:`;
   - код фаз пула (Шаг 5): в `generating` — их целевые файлы по плану и новые файлы `domain/`; в `written` — только `phases.N.files`;
   - `sys_id`, которые дописал `patch`, ещё не закоммиченные (CLI пишет их и при провале): изменённые файлы диапазона этого `patch`;
   - файлы финального фона (Шаги 6–7), пока он не закоммичен: `_demo_plan.md`, `_demo_data.json`.

   `patch --commit` и `build` берут только закоммиченное. В режиме `deploy = tree` пул — одна фаза, и во время `patch` генерация не идёт.
4. В `git status --porcelain` осталось что-то ещё — вне наборов или внутри них, в том числе в `domain/` (например, файл исправления, которого нет в отчёте) → стоп со списком файлов. Ничего не удалять и не прятать.

**Git.**
- Push — только `git push -u origin <ultra.branch>`.
- **Ветка сменилась извне.** Перед каждой точкой фиксации и коммитом — `git branch --show-current` = `ultra.branch`. Не совпадает (переключили снаружи) → не переключать самому: стоп с вопросом «рабочая копия на `<ветка>`, прогон — на `<ultra.branch>`: вернуть?». Вернуть — только по ответу человека, и только если в дереве нет чужих незакоммиченных изменений.
- Запрещены: `git stash`, `git checkout -- <путь>`, `git restore`, `git clean`, `git reset --hard`.
- Hook упал → `code-author` (fix) по выводу hook, повторить коммит. Снова упал → стоп. `--no-verify` запрещён.
- Hook переписал файлы при коммите (например, `eslint --fix`) → сверить `git show --stat HEAD` и дифф с тем, что сдал агент: логика не должна измениться. Изменилась → `code-author` (fix) и новый коммит. Если hook оставил незакоммиченные правки — добавить их в следующий коммит той же работы.

**Деплой.**
- Режим `ultra.options.deploy` (Шаг 0):
  - `commit` — `patch --commit <ultra.deployed_head>..HEAD`, первый деплой — `--commit <initial_commit_sha>..HEAD`: только закоммиченное, рабочая папка не участвует;
  - `tree` — обычный `patch`, от `last_patch` до рабочей папки.
- После `patch` — коммит write-back (`chore: <task_id> — sys_id write-back`), если CLI дописал `sys_id` в DSL: только файлы, которые дописал CLI. После `build` write-back входит в коммит `build:` (Шаг 7 п. 4).
- После коммита write-back (или сразу после деплоя, если его нет) — `ultra.deployed_head = HEAD`: это состояние стенда.
- Нужен ли `patch`, решается по состоянию, а не по памяти: `git diff --name-only <ultra.deployed_head> HEAD -- <product>/domain/` не пуст или деплоя ещё не было. Write-back в этот дифф не попадает, лишних патчей нет.

**Правило очерёдности.** Два писателя в одни файлы одновременно не работают:
- `patch` дописывает `sys_id` в файлы деплоя, поэтому не запускается, пока `code-author` правит те же файлы;
- два `code-author` (фазы пула, исправления) работают одновременно, только если их файлы не пересекаются.

Файлы работы известны заранее: у фазы — целевые файлы её задач в плане, у исправления — файлы из ISSUE или дефекта. Пересекаются → ждать, пока закончит тот, кто начал раньше. Поэтому фаза пула меняет только целевые файлы своих задач и создаёт новые: оркестратор передаёт ей строку `Только свои файлы: <целевые файлы>`. Другой существующий файл (общая локализация, навигация, файл другой фазы) — только через `ULTRA_FOREIGN`, даже если его нет в `Чужая работа`.

**Чужая работа.** Каждому `code-author` оркестратор передаёт строку `Чужая работа: <файлы>` — файлы другого `code-author`, которые сейчас пишутся или лежат незакоммиченными: фаз пула в `generating` / `written` и незакоммиченных исправлений.

Командам, которые вызывают `code-author` (`code_generate`, `product_patch`), эта строка передаётся в аргументах. Чужие файлы `code-author` не правит. Если они ему нужны, он возвращает `ULTRA_FOREIGN` (формат — `code-author`):
- **от фазы пула** → `phases.N.foreign`; `code-author` (fix) по этим пунктам, как только работа, которой принадлежат файлы, закоммичена (Шаг 5);
- **от исправления** (ревью, дефект, ошибка деплоя) → склейка: дождаться фазы, которой принадлежат файлы (`written`), выполнить её `foreign`, если он не пуст, закоммитить её `feat:` и повторить исправление. Дальше эта фаза деплоится той же пачкой и ревьюится вместе с фазами исправления, счёт итераций ревью — заново; в журнал — «склеена с фазой N».

**Вызовы `test-author`.** Каждому вызову передавать порцию и `deployed_sha = ultra.deployed_head`. Порции: `воспроизведение` (дефект, до кода), `final` (все тесты до `build`), `после build`. Режимы `fix` и `rerun` получают метку текущей порции.

**Итерации и уведомления.**
- Циклы ревью — не более 3; исправление одного дефекта или одной ошибки деплоя — не более 3 попыток. Исход — по стоп-условиям `ultra-rules`.
- Если в IDE есть push-уведомления — отправлять при стопе и при готовом MR.

## Шаг 0: Pre-flight (`preflight`)

Здесь вопросы ещё можно задавать: прогон не начался.

1. **Версия.** `version` из `.simplegen/state.json` vs `simplegen --version`: CLI ниже — `npm update @simplegen/simplegen`; выше — `/simplegen.init`; не совпадают → стоп. Вложенные команды с `--ultra` версию повторно не проверяют.
2. **Продукт** — каталог верхнего уровня с `AGENTS.md`: один — авто, несколько — спросить.
3. **Задача.** `<product>/tasks/<task_id>/` существует:
   - есть `_local/ultra.json` со `status` `stopped` / `running` → предложить `/simplegen.ultra resume`;
   - нет `_local/ultra.json`, есть `_spec.md` — задачу начали поэтапно, спека — аналитика. Если в аргументах не сказано, что продолжаем по ней, — спросить: «Продолжить ultra с существующей спекой» / «Стоп». При продолжении:

     - готовые фазы определяются после возврата `plan-author` разведки (merge, Шаг 1) по плану после merge: фазы, где все задачи `[x]`, получают `code: generated`, `review: done` и снимок `tasks`. Их код уже есть: дальше они заморожены (Шаг 4 п. 5), конвейер не генерирует и не коммитит их заново (Шаг 5), код проверит финальное ревью. `initial_commit_sha` пуст → `git merge-base HEAD <целевая ветка>`, как база CLI по умолчанию: иначе Шаг 4 п. 4 выставит HEAD, и `build`, `verify` и финальное ревью не увидят код этих фаз;
   - нет `_local/ultra.json` и нет `_spec.md` → стоп: каталог задачи занят, нужен другой ID.

   Новой задаче — `ultra.spec_owner = ultra`: спеку пишет `spec-author` на разведке.
4. **Git.**
   1. **Рабочее дерево не чистое:**
      - изменены только файлы самого SimpleGen после `simplegen init` или обновления пакета: `.claude/`, `.opencode/`, `.simplegen/state.json`, `AGENTS.md`, `.gitignore`, `eslint.config.mjs`, `jsconfig.json`, `simpleone-api.d.ts`, `api-index/`, `package.json`, `package-lock.json`, githooks. Это обновление SimpleGen — в ветку задачи и в её MR оно не идёт. Стоп: «Закоммитьте обновление SimpleGen в целевую ветку отдельным MR (или уберите его) и перезапустите прогон»;
      - есть что-то ещё (код `domain/`, задачи, прочее) → стоп: закоммитить или убрать изменения.
   2. Detached HEAD → стоп: нужна ветка.
   2a. **Обновление SimpleGen уже в ветке.** `git diff --name-only <целевая>...HEAD` (нет локальной целевой ветки → `origin/<целевая>`; нет и её → предупреждение «целевая ветка не найдена на origin») затрагивает файлы SimpleGen из п. 1 → предупреждение на интервью: «В MR попадёт обновление SimpleGen: N файлов. Вынесите его в отдельный MR в целевую ветку до прогона». В MR — флаг 🔴 с этим списком.
   3. **Целевая ветка** — так же, как её ищет CLI. Все сравнения с ней — через `origin/<целевая>`, если локальной ветки нет. Целевая ветка MR отличается от `SIMPLEGEN_TARGET_BRANCH` в `.env` → предупреждение на интервью: CLI сужает пакет относительно ветки из `.env`.

   Порядок поиска:
      - `SIMPLEGEN_TARGET_BRANCH` — из окружения, иначе из `.env`;
      - иначе `git symbolic-ref --short refs/remotes/origin/HEAD`;
      - иначе `master`, затем `main`.

      Префикс `origin/` отбросить.
   4. **Общие ветки** — целевая, ветка `origin/HEAD`, `master`, `main`, `develop`. В общие ветки прогон не коммитит никогда.
   5. **Текущая ветка — единственная ветка прогона.** Новых веток прогон не создаёт и веток не переключает никогда: ни `git switch -c`, ни `git checkout -b`, ни `git branch <имя>`, ни `git switch <ветка>`. Все коммиты прогона — в текущую ветку.
      - текущая — общая → стоп: «Прогон работает в текущей ветке и в общие ветки не коммитит: перейдите в ветку задачи и запустите снова». Ветку создаёт человек;
      - иначе → работать в ней, имя ветки может быть любым.

   Итог — `ultra.branch` (текущая), `ultra.target_branch`.
   6. **Локальные тесты в `.gitignore`.** Каждый путь — отдельным `git check-ignore -q`: с несколькими путями команда успешна, если игнорируется хоть один. Пути: `<product>/tasks/<task_id>/_local/x`, `.simplegen/e2e/x`, `.playwright-mcp/x`. Для неигнорируемых дописать их строки (`**/tasks/*/_local/`, `.simplegen/e2e/`, `.playwright-mcp/`) в `.gitignore` и закоммитить в ветку задачи: `chore: ignore ultra local tests`.
5. **Стенд.** `simplegen demo whoami`: стенд доступен, `User`, `is_admin`. Недоступен → стоп с выводом CLI.
   - `User` = `SIMPLEONE_LOGIN` → `impersonate_access` из whoami годится для предупреждения на интервью.
   - `User` ≠ `SIMPLEONE_LOGIN` (CLI вошёл по `SIMPLEONE_API_KEY`) → предупреждение: деплой идёт под `User`, браузер и Playwright — под `SIMPLEONE_LOGIN`. Доступность имперсонации проверит `test-author` по меню в браузере.
6. **Режим деплоя.** В выводе `simplegen --help` у `--commit` есть «the working tree is not used» → `ultra.options.deploy = commit`: CLI деплоит ровно коммиты, и следующую фазу можно генерировать заранее. Иначе `deploy = tree`, фазы строго по очереди.
7. **Инструменты** — нет инструмента → предупреждение на интервью, не стоп:
   - браузерные инструменты в IDE — для прогона кейсов агентом. Имена зависят от IDE (`browser_navigate`, `browser_snapshot`, `mcp__Claude_Browser__navigate`, …): годится любой набор «открыть страницу, прочитать, кликнуть». Если политика IDE не даёт агенту вводить пароли на стенде — на интервью попросить человека заранее войти в браузере IDE под `SIMPLEONE_LOGIN`;
   - **e2e-фреймворк продукта** — проверяется первым. Признаки: сабмодуль или каталог с Playwright-фреймворком команды тестирования (например, `playwright-core/` с `autotests-core`), каталог хелперов продукта (`<product>/tests/*-e2e-core/`), тесты с фикстурами данных (`<product>/tests/e2e/**/*.fixtures.*`), скрипты фреймворка в корневом `package.json` (`pw-core:init`, `test`).
     - Найден и готов — проверяется по файлам, а не по каталогам: `git submodule status` без `-` у сабмодуля, зависимости установлены (`<сабмодуль>/node_modules/@playwright/test` или пакет раннера, который называет README фреймворка), браузер в кэше Playwright → `ultra.options.e2e = product`: тесты пишутся и запускаются его средствами, данные создают его фикстуры (`test-author`, «Фреймворк продукта»). Свой Playwright в `.simplegen/e2e/` не ставится.
     - Найден, но не готов → на интервью предлагается подготовить его штатной командой продукта (`pw-core:init`, установка зависимостей по его README). Отказ или ошибка → `e2e = own`.
     - Не найден → `e2e = own`, дальше — свой Playwright ниже.
   - Playwright (только при `e2e = own`) — готов, только если есть всё:
     - `.simplegen/e2e/playwright.config.ts` с `globalSetup` и `storageState`, `.simplegen/e2e/global-setup.ts` и `.simplegen/e2e/simpleone.ts`;
     - `node_modules/@playwright/test`;
     - браузер: `node -e "const {chromium}=require('@playwright/test');process.exit(require('fs').existsSync(chromium.executablePath())?0:1)"` завершается кодом 0.

     Чего-то нет → «не установлен»: на интервью предлагается установка, `scaffold` создаст недостающее, не трогая существующее;
   - вход по логину: `SIMPLEONE_LOGIN` / `SIMPLEONE_PASSWORD`. Без них ни прогон в браузере, ни Playwright не войдут на стенд;
   - MR: `glab auth status`; `git remote get-url origin` — GitLab ли remote; bash (на Windows — Git Bash) для команд git и MR;
   - **Figma** — только если в постановке или в `_spec.md` есть ссылки `figma.com`. Проверить, что Figma MCP подключён и отвечает: один вызов метаданных по первой ссылке (`get_metadata` или аналог; имена инструментов зависят от IDE — годится любой инструмент Figma MCP с получением узла макета). Отвечает → `ultra.options.figma = mcp`. Не подключён, требует авторизации или ошибка доступа к файлу → `figma = none` и предупреждение на интервью. Ссылок нет → `figma` не ставить.
8. **Тексты интерфейса** — продуктовый скилл `simplegen.texts_update`, в шаблонах SimpleGen его нет. `ultra.options.texts = true`, если есть оба:
   - реестр `<product>/texts/interface-texts.md`;
   - скилл в репо продукта для текущей IDE: `.claude/skills/simplegen.texts_update/SKILL.md`, `.opencode/commands/simplegen.texts_update.md`, `.kilo/commands/simplegen.texts_update.md` или `.cursor/commands/simplegen.texts_update.md`.

   Иначе `texts = false`: шаг пропускается молча, без предупреждения и флага.

## Шаг 1: Разведка (`recon`)

Цель — собрать **все** вопросы до интервью. Субагенты работают в `Режим: ultra:collect`.

**До старта агентов** — состояние прогона `_local/ultra.json` задачи: `status: running`, `stage: recon`, `done: ["preflight"]`, `branch`, `target_branch`, `spec_owner`. Своя спека: каталога ещё нет → создать `<product>/tasks/<task_id>/` с `simplegen.json` = `{}` и `_local/ultra.json`, выставить активную фичу (`simplegen context <product> <task_id>`). Без этого шага прерванная разведка оставит черновик без состояния, и повторный запуск примет его за спеку аналитика. Там же создать `_local/_ultra_log.md` с разделом «Постановка»: описание, AC-N, ссылка на Figma, секреты — `***`. Resume берёт постановку только из журнала.

**Без барьеров.** Агенты разведки — фоновые. Каждый стартует, как только готов его вход, не дожидаясь остальных агентов своей «волны»:

| Агент | Стартует, когда | Вход |
| ----- | --------------- | ---- |
| `criteria-assessor` | сразу, если критерии есть | критерии приёмки, бизнес-описание |
| `spec-author` (create) | сразу; **только при `spec_owner = ultra`** | `task_id`, описание, критерии в исходном порядке (AC-N), Figma, продукт. Пишет в каталог, созданный оркестратором, `_spec.md`, `changelog.md`, `build_logs/`; `simplegen.json` не трогает |
| `spec-reviewer` | есть `_spec.md`: сразу при спеке аналитика, после `spec-author` — при своей | критерии, исходное описание, `spec_owner` |
| `plan-author` (create или merge, если план уже есть) | тогда же, что `spec-reviewer`, одним сообщением с ним | черновик `_task_plan.md` по спеке и разделу «Для таск-плана» журнала |
| `plan-reviewer` | вернулся `plan-author` — не дожидаясь `spec-reviewer` | нужны только его `NEEDS_USER_INPUT` и `PHASE_VERDICTS`; `AUTO` исправятся на Шаге 4 |

Пока агенты работают, оркестратор сам определяет роли для тестов (ниже). Так разведка спеки аналитика укладывается в одну волну: `criteria-assessor` ∥ `spec-reviewer` ∥ `plan-author`, затем `plan-reviewer`.

Секреты из постановки (пароли, токены, ключи) заменить на `***` до передачи агентам.

**Спека аналитика** (`spec_owner = analyst`):
- `spec-author` (create) не запускать;
- активную фичу выставить самому: `simplegen context <product> <task_id>`;
- «Постановка» в журнале — из аргументов. Если их нет — «спека создана поэтапно до ultra», критерии — «не переданы»;
- после возврата `plan-author` — `ultra.phases` для фаз, готовых до прогона (Шаг 0 п. 3).

Вернулся `spec-author` — раздел «Для таск-плана» из его отчёта в одноимённый раздел журнала, до старта `plan-author`.

**Роли для тестов** — роли, под которыми будут кейсы, и роли, отсутствие которых проверяют негативные кейсы: из матрицы доступов спеки.

**Собрать вопросы:**
- вердикт `criteria-assessor`: `WARN` — замечания, `DECOMPOSE` — предложенное разделение;
- `ULTRA_QUESTIONS` от `spec-author` и `plan-author`;
- вопросы и `NEEDS_USER_INPUT` от `spec-reviewer` и `plan-reviewer`.

Один и тот же вопрос из нескольких источников — один пункт. Агенты рекомендуют разное → рекомендуемым берётся вариант ближе к спеке и с меньшим объёмом, в журнале — кто что рекомендовал. Порядок: бизнес → тех. решение → пользователи для ролей.

**Спека аналитика — что делать с её замечаниями:**
- вопросы и `NEEDS_USER_INPUT` к спеке идут в интервью как обычно, но ответ ложится в план, а не в спеку;
- у вопросов с приоритетом 🔴 (непокрытый критерий, противоречие, неясное поведение) — ещё и выбор: «Оставить уточнением в таск-плане (рекомендуется)» / «Проигнорировать». В тексте вопроса — подсказка: если спеку нужно исправить, ответьте «Стоп» на последний вопрос: спеку дорабатывает аналитик;
- `AUTO`-замечания к спеке (формат, структура, переводы, детали реализации в тексте) не исправляются: они идут в журнал, раздел «Замечания к спецификации», а оттуда в MR — для аналитика.

**Конец разведки:**
- вопросы — в таблицу «Интервью» журнала: варианты и рекомендация есть, ответов пока нет;
- `ultra.done += recon`.

На разведке ничего не коммитится.

## Шаг 2: Интервью (`interview`) — единственная остановка

**Фон, пока человек отвечает** — только при спеке аналитика: она не изменится, и артефакты по ней не устареют. Перед первым вопросом, фоновыми субагентами, одним сообщением:
- `diagram-author` по `_spec.md` (`/simplegen.diagrams_build --ultra`) → `background.diagrams_spec`;
- `test-author` (cases, черновик) — кейсы по спеке, без фаз: фазы и `У-N` появятся после цикла плана → `background.cases`.

Они пишут только свои файлы и ничего не коммитят: коммит — в первой точке фиксации после интервью. Ответ «Стоп» или «Делим» → дождаться их и оставить файлы незакоммиченными. Своя спека или IDE без фоновых субагентов → всё это стартует на Шаге 4 п. 7, как раньше.

Показать по порядку:

1. **Сводка:** сколько UC / FR, какие таблицы и роли затронуты, фазы плана, вердикт `criteria-assessor`, чья спека, режим деплоя.
2. **Предупреждения**, первым — про учётку:

   > ⚠️ Деплой пойдёт под учёткой `<User из whoami>` на `<SIMPLEONE_URL>`. `patch` и `build` переключают текущий локальный пак этой учётки: если под ней сейчас работают люди, их правки попадут в пак задачи `<task_id>`, а их текущий пак сменится. Тесты на стенде под `<SIMPLEONE_LOGIN>` создадут записи с префиксом `[TEST <task_id>]` и будут имперсонироваться под тестовых пользователей; удалять записи прогон не будет.

   Затем найденное на Шаге 0:
   - нет имперсонации (по whoami, когда `User` = `SIMPLEONE_LOGIN`) → кейсы под ролями пойдут в SKIP. Право не выдаётся автоматически: выдать роль `impersonator` может только человек;
   - нет браузера → прогон кейсов агентом пропускается, Playwright-тесты не из чего писать;
   - Playwright не установлен и установку не выбрали → кейсы пойдут через браузер IDE: он может спрашивать подтверждение на каждый клик и каждый запуск JavaScript на стенде. С Playwright порция — одна команда;
   - агенту нельзя вводить пароли (политика IDE) → «Войдите на стенд в браузере IDE под `<SIMPLEONE_LOGIN>` до ответа „Поехали“: прогон работает в открытой сессии»;
   - `deploy = tree` → фазы строго по очереди: обновите SimpleGen, чтобы следующая фаза писалась, пока деплоится текущая;
   - нет `glab` → MR через push options; remote не GitLab → MR не создаётся;
   - `figma = none` → «Figma MCP недоступен: <причина>. Авторизуйте его (в Claude Code — `/mcp`) и перезапустите прогон, или приложите скриншоты макетов к ответу — тогда интерфейс делается по ним».
3. **Декомпозиция** (только при `DECOMPOSE`) — первым вопросом: «Делаем одной задачей» / «Делим — прогон останавливается, вывожу предложение».
4. **Вопросы пакетами.**
   - Первым — «Принять все рекомендации» / «Пройти вопросы по одному». Первое закрывает все вопросы рекомендуемыми вариантами, кроме тех. решения и «Поехали».
   - Если есть инструмент вопросов с вариантами (AskUserQuestion) — до 4 вопросов за вызов, до 4 вариантов, рекомендуемый первым с пометкой «(рекомендуется)».
   - Иначе — нумерованный список с вариантами и подсказкой формата: `Q1: A, Q2: свой ответ`; «по умолчанию» = все рекомендуемые.
5. **Техническое решение:** таблица «Предварительное техническое решение» из черновика плана (требование → выбор → обоснование). Вопрос: «Принять» / «Поправить — опишите что».
6. **Опции прогона:**
   - Демо: «План + демоданные файлом в MR (рекомендуется)» / «Только план» / «Без демо». На стенд демоданные не применяются.
   - Пользователи для кейсов под ролями (если такие кейсы есть):
     - при `e2e = product` — вопроса нет: пользователей с нужными ролями создают фикстуры фреймворка;
     - при `e2e = own` — «Назову сам: роль → пользователь (логин)» / «Кейсы под ролями пропустить».

     Под другими пользователями прогон не имперсонируется.
   - Только при `figma = none` — макеты: «Приложу скриншоты, остальное по рекомендациям (рекомендуется)» / «Без макетов: интерфейс по спеке и стилям продукта» / «Стоп: авторизую Figma MCP». Вместе со скриншотами — всё, что без MCP не извлечь: hex-цвета, шрифты, SVG-иконки, состояния (hover, disabled, ошибка). Чего не дали — допущение `[макет]` по стилям продукта. Итог — `options.figma`: `screenshots` / `skip`; скриншоты сохранить в `_local/figma/` и передавать агентам пути к ним.
   - Только при `e2e = product`, если фреймворк не готов: «Подготовить e2e-фреймворк продукта: <команда из его package.json или README> (рекомендуется: готовые фикстуры данных и вход)» / «Свой Playwright в `.simplegen/e2e/`».
   - Только если `e2e = own` и Playwright не установлен: «Развернуть Playwright локально в `.simplegen/e2e/` — `@playwright/test` без записи в `package.json` и браузер Chromium (рекомендуется)» / «Без Playwright».
7. **Последний вопрос — «Поехали?»:** «Поехали (рекомендуется)» / «Стоп». Ответ «Поехали» — согласие ровно на список из раздела «Безопасность» `ultra-rules`.

**Ответ против макета.** Ответ интервью расходится с макетом Figma (`figma = mcp`): например, выбран вариант с элементом, которого в макете нет, или поведение, которого макет не показывает. Тогда в том же интервью, до «Поехали», — уточняющий вопрос со ссылкой на кадр: «В макете <что есть>. Делаем по макету (рекомендуется) / по ответу Q<N>, без макета». Молча расходиться с макетом нельзя.

**После ответов:**
- ответы — в таблицу «Интервью» журнала (секреты — `***`);
- решения уровня реализации (тех. решение, «Поправить») — в раздел «Для таск-плана»;
- спека аналитика: бизнес-ответы любого источника — `spec-reviewer`, `plan-author` («бизнес»), `plan-reviewer`, `criteria-assessor`, — кроме «Проигнорировать», в «Для таск-плана» с пометкой «уточнение к спецификации». `spec_create` не вызывается, `plan-author` получает только тех. ответы: другого пути в план у них нет; «Проигнорировать» — в «Замечания к спецификации»;
- в `ultra.options` — значения по схеме `ultra-rules`:
  - `demo`: `plan+data` / `plan` / `none`;
  - `playwright`: `true` — установлен или выбрана установка;
  - `role_users`: `fixtures` (при `e2e = product`) / карта «роль кейса → логин» / `skip`;
  - `deploy`: из Шага 0;
- в `ultra`: `stand_url` (`SIMPLEONE_URL`), `deploy_user` (`User` из whoami), `login` (`SIMPLEONE_LOGIN`) — согласие дано на них;

**«Стоп» или «Делим»:**
- `ultra.status = stopped`, `stop_reason` — ответ;
- ничего не коммитить;
- в итоге перечислить, что осталось: незакоммиченный каталог задачи, активная фича в `.env`. Варианты: вернуться позже через `/simplegen.ultra resume` или удалить черновик — по просьбе человека. Ветку прогон не переключает.

Иначе `ultra.done += interview`. Дальше вопросов нет.

## Шаг 3: Спека (`spec`)

**Своя спека** (`spec_owner = ultra`) — `/simplegen.spec_create --ultra`. Вход: бизнес-ответы интервью (`ULTRA_ANSWERS`), исходное описание и критерии AC-N из «Постановки». `spec-author` (fix) вносит ответы, затем цикл ревью с проверкой покрытия критериев.

Новые пункты «Для таск-плана», `ULTRA_ASSUMPTIONS` и флаги — в журнал. Коммит `spec: <task_id>`: `_spec.md`, `changelog.md`, `simplegen.json` задачи.

**Готовая спека** (`spec_owner = analyst`) — этап пропускается: `ultra.done += spec`, сразу Шаг 4.

## Шаг 4: План и старт кода (`artifacts`)

Код не ждёт ни конца цикла плана, ни документации и диаграмм.

1. **Цикл плана ведёт сам оркестратор** по шагам `/simplegen.spec_plan --ultra`. Команду целиком через Skill не вызывать: она заняла бы оркестратор до конца цикла.
   - `plan-author`, `plan-reviewer` и `spec-author` (если цикл его вызывает) работают фоновыми субагентами. Кодовая полоса тем временем идёт в основном потоке.
   - По уведомлению о завершении субагента плана — следующий шаг цикла. `SPEC_REMARKS` от `plan-reviewer` — в журнал, «Замечания к спецификации», и следующему `plan-author` (fix): детали реализации из них — в техническое решение.
   - Вход `plan-author`: тех. ответы интервью, раздел «Для таск-плана» журнала, постановка, `spec_owner`.
   - **Первый шаг цикла — `plan-author` (fix)** по ответам интервью и `AUTO` разведки. Ревью разведки повторно не запускается.
   - **Цикл останавливают только 🔴.** После `plan-reviewer`:
     - `PASS` → конец цикла;
     - среди ISSUES нет 🔴 → последний `plan-author` (fix) по ним и конец цикла, без нового ревью;
     - есть 🔴 → `plan-author` (fix), затем `plan-reviewer`. Не более 3 ревью за цикл: после третьего FAIL — последний `plan-author` (fix) без ревью, его ISSUES — в журнал как «исправлено без перепроверки», оставшиеся 🔴 — флаги.
   - `ultra.plan_loop = running`. IDE без фоновых субагентов → цикл плана до конца, затем Шаг 5 без перекрытия.
2. **Готовая фаза** — готовы все фазы из её «Зависимостей» и:
   - её участок плана проверен: `PASS` в последних `PHASE_VERDICTS`, и после этого ревью `plan-author` не менял фазу — её нет в `PHASES_TOUCHED` ни одного вернувшегося с тех пор `plan-author` (fix);
   - или цикл плана уже закончен (`plan_loop = done`).

   `PHASE_VERDICTS` разведки тоже в счёт: фаза, которую первый `plan-author` (fix) по ответам интервью не тронул, готова сразу после его возврата. Ответы интервью меняют обычно одну-две фазы, остальные уходят в код без ожидания ревью.
3. **Окно заморозки.** Пока идёт цикл плана, фазы замораживаются, только когда `_task_plan.md` никто не пишет: после возврата `plan-reviewer` или `plan-author` (fix) и до запуска следующего `plan-author` (fix). Перед каждым `plan-author` (fix) замораживаются все фазы, готовые по п. 2. Заморозка — снимок задач фазы в `ultra.phases.N.tasks`: именно их увидит `code-author`. Замороженная фаза стартует в любой момент без повторной проверки, в том числе пока работает `plan-author`. Кодовая полоса освободилась, а следующая фаза не заморожена → ждать следующего возврата агента плана.
4. **Старт кода** первой фазы: `initial_commit_sha` пуст → `git rev-parse HEAD`, до первого коммита кода. `ultra.stage = pipeline`, дальше — Шаг 5. `build` и `verify` берут из диффа `initial_commit_sha..HEAD` только DSL, ревьюер кода — только набор «Код».
5. **Пока цикл плана идёт:**
   - список замороженных фаз получают `plan-author` (fix) и `plan-reviewer` на каждой итерации. Правки, которые их задевают, приходят задачами-доработками в ближайшую более позднюю незамороженную фазу или в новую последнюю фазу «Доработки»;
   - `_task_plan.md` `code-author` в режиме ultra не трогает никогда (`code-author`, «Режим ultra»): `[x]` ставит оркестратор. Пока цикл идёт, `_task_plan.md` не входит ни в один коммит кодовой полосы.
6. **Конец цикла плана** — PASS, последний `plan-author` (fix) без ревью или лимит ревью (п. 1):
   - `[x]` — задачам из `phases.N.tasks` фаз, чей `feat:` уже сделан (`code` = `generated` / `deployed`). Остальные фазы получают `[x]` в своём `feat:`;
   - задача замороженной фазы вне её снимка (появилась после заморозки) → флаг «доработка не реализована»;
   - коммит `plan: <task_id>`: `_task_plan.md`; при своей спеке — также `_spec.md` и `changelog.md`, если цикл вернул правки в спеку;
   - `ultra.plan_loop = done`.
7. **Фоновые артефакты** — после конца цикла плана, фоновыми субагентами, параллельно кодовой полосе. В `domain/` и `_task_plan.md` они не пишут. Начатые во время интервью (Шаг 2) не повторяются, а сверяются с планом: `У-N` и фазы появились только сейчас.
   - **Волна 1** — читают спеку и план, пишут разные файлы:
     - `test-author` (cases): `_local/test_cases.md`, локально. Каждый кейс — с фазами плана, после которых он выполним, и ролью. Черновик с интервью есть → `test-author` (cases) дополняет его: фазы, тексты по `У-N`, кейсы для `У-N`; номера TC не меняются;
     - `texts` — при `options.texts = true`: фоновый субагент по скиллу `simplegen.texts_update` (путь из pre-flight; через Skill не вызывать — займёт оркестратор). Скилл режима ultra не знает, поэтому в задании — отличия:
       - строка `Режим: ultra:auto`, `current_feature_path` — из `simplegen.json` задачи;
       - Шаг 0 (версия) пропустить: её проверил pre-flight;
       - источники текстов — `_spec.md` и раздел плана «Уточнения к спецификации» (`У-N`): при спеке аналитика тексты из интервью живут там. Расхождение — по `У-N`;
       - пишет только `<product>/texts/interface-texts.md`. Ничего не спрашивать: текста на одном языке нет в спеке → не придумывать, строку оставить с пустой ячейкой и дать `ULTRA_ASSUMPTIONS` `[тексты] <сущность> / <тип> → нет <EN|RU> в спеке`;
       - отчёт завершить блоками `ULTRA_ASSUMPTIONS` / `ULTRA_BLOCKED` по `ultra-rules`;
     - `test-author` (scaffold) — при `e2e = product` не запускается: инфраструктура — фреймворка. При `e2e = own` — если выбрана установка Playwright. Всё локально: файлы в `.simplegen/e2e/`, пакет — `npm install --no-save`. Ошибка → `options.playwright = false`, флаг.
   - **Волна 2** — после возврата `test-author` (cases), если диаграммы спеки не начаты на интервью: `diagram-author` по `_spec.md` (`/simplegen.diagrams_build --ultra`). При своей спеке он пишет раздел «Диаграммы» в `_spec.md`, который читает волна 1. Готовую спеку не трогает: диаграммы — только отдельными файлами рядом, «Замечено в исходнике» — в журнал, «Замечания к спецификации».
   - `diagram-author` по `_task_plan.md` — в хвосте конвейера (Шаг 5): кодовая полоса ставит `[x]` в том же файле.

   Статусы — `ultra.background`: `""` → `running` → `done` (готов, не закоммичен) → `committed`. Локальные `cases` и `scaffold` не коммитятся и остаются в `done`. Коммит готового — в ближайшей точке фиксации:
   - `docs: interface texts for tasks/<task_id>` — `<product>/texts/interface-texts.md`; файл не изменился → коммита нет, статус `committed`;
   - `docs: diagrams for tasks/<task_id>` — созданные и удалённые `*.puml`, `*.svg`, `*_diagrams.md` из отчёта агента и раздел «Диаграммы» исходника: `_task_plan.md` или своей `_spec.md`.

8. **Воспроизведение дефекта** — только если задача — дефект (в постановке или спеке есть шаги воспроизведения, ожидаемый и фактический результат). Фоном, сразу после интервью, до первого `patch`: `test-author` (run), порция `воспроизведение` → `background.repro`. Он проверяет, есть ли на стенде данные для сценария, и проходит шаги воспроизведения на текущем коде.
   - Дефект воспроизвёлся → в журнал, это доказательство; кейс воспроизведения войдёт в финальные тесты.
   - Данных нет → флаг «дефект не воспроизведён: нет данных», прогон идёт дальше. Данные для сценария создаст фикстура фреймворка в финальных тестах.
   - Не воспроизвёлся при наличии данных → флаг «дефект не воспроизведён», прогон идёт дальше.

   Первый `patch` ждёт его возврата: стенд не меняется под проверкой.

## Шаг 5: Конвейер фаз (`pipeline`)

Фазы пишутся пулом и деплоятся очередью. Тестов на фазах нет: всё тестирование — в финале, на `patch`-стенде (Шаг 7). На фазах код проверяют ревью и сам деплой.

**Состояние фазы** `ultra.phases.N`:
- `tasks` — снимок задач фазы на момент заморозки (Шаг 4 п. 3) или старта; непустой `tasks` — фаза заморожена;
- `code`: `""` → `generating` → `written` (`code-author` вернулся, код не закоммичен) → `generated` (коммит `feat:` сделан) → `deployed` (патч прошёл);
- `foreign`, `files` — невыполненные `ULTRA_FOREIGN` фазы; файлы её отчёта и исправлений по `foreign`: по `files` коммит `feat:`, после него оба поля пусты;
- `base` — HEAD перед коммитом `feat:` фазы, пишется один раз;
- `commits` — коммиты фазы: `feat:` и исправления её ревью. По ним идёт ревью фазы: в истории коммиты разных фаз перемешаны, поэтому диапазон `base..HEAD` для этого не годится;
- `review`: `""` → `done`.

**Пул генерации.** Одновременно работает до 3 `code-author` (generate). Фаза стартует, когда:
- она готова (Шаг 4 п. 2–3) и её `code` пуст;
- все фазы из её «Зависимостей» уже `generated` / `deployed`: их код закоммичен, на него можно ссылаться;
- её целевые файлы по плану не пересекаются ни с целевыми файлами фаз в `generating`, ни с `files` фаз в `written`, ни с файлами незакоммиченных исправлений.

При `deploy = tree` пул — одна фаза, и пока идёт `patch`, генерация не стартует: обычный `patch` забрал бы незакоммиченный код.

**Старт фазы:** снимок `tasks`, если его ещё нет; `code: generating`; `code-author` (generate N) фоном, со строками:
- `Только свои файлы: <целевые файлы задач фазы>`;
- `Чужая работа: <целевые файлы остальных фаз пула, файлы незакоммиченных исправлений>`.

Несколько стартов — одним сообщением. Лимит API общий на всю сессию: вместе с фоновыми артефактами одновременно не больше 5 субагентов, фазы ждут места.

**Агент вернулся** → `code: written`, `files` и `foreign` — по его отчёту. Дальше:
1. `foreign` не пуст → `code-author` (fix) по этим пунктам, как только работа, которой принадлежат нужные файлы, закоммичена. Файлы его отчёта дописать в `files`, `foreign` очистить.
2. **Коммит.** `base` пуст → `git rev-parse HEAD`. Коммит `feat: <task_id> — фаза N <название>` по `files`. Пока идёт цикл плана — без `_task_plan.md`; после цикла — вместе с `[x]` задач снимка. `commits += <sha>`, `files` очистить, `code: generated`.
3. Место в пуле — следующей готовой фазе.

Коммиты фаз идут в порядке готовности, а не в порядке плана. Зависимости при этом соблюдены: фаза стартует только после коммита своих зависимостей.

Фаза с `code` = `generated` / `deployed` (готова до прогона, Шаг 0 п. 3) не генерируется и не коммитится заново.

**Очередь деплоя.** `patch` — один за раз. Освободился и есть фазы `generated` →
1. Точка фиксации → `patch`, если нужен по правилу деплоя:
   - `deploy = commit`: `/simplegen.product_patch --ultra --commit <ultra.deployed_head>..HEAD`, по правилу очерёдности;
   - `deploy = tree`: `/simplegen.product_patch --ultra`.
2. → коммит write-back, `ultra.deployed_head = HEAD`, `code: deployed` всем фазам пачки.

Пачка — всё, что закоммичено к запуску: одна фаза или несколько, специально никого не ждать. **Копить фазы до конца запрещено:** после каждого `feat:` очередь проверяется сразу, и свободный `patch` запускается, не дожидаясь генерации остальных фаз. Ревью пачки — сразу после её деплоя, а не в конце. Пока идёт `patch`, пул работает дальше: `patch --commit` берёт только закоммиченное.

**Ревью пачки** — после её деплоя: `/simplegen.code_generate --ultra review <фазы пачки через запятую>`. Ревьюер получает `commits` этих фаз, а не диапазон. Фазы с `review = done` (готовы до прогона) — не в счёт.
- Ревьюер только читает закоммиченное: пул и очередь деплоя работают во время ревью.
- Исправления — `code-author` (fix) по правилу очерёдности, коммит после каждой итерации внутри команды, `commits` своей фазы += коммит.
- Исправления деплоятся следующей пачкой очереди. `review: done` — фазам пачки.

**После последней фазы** — только при `plan_loop = done`: последняя фаза определяется по финальному плану. Пока цикл идёт, конвейер ждёт его конца; фазы, которые цикл добавил («Доработки»), идут по обычным правилам.
1. Все фазы `deployed` и `review: done`, исправления ревью задеплоены.
2. **Хвост фона:**
   - `diagram-author` по `_task_plan.md` (`/simplegen.diagrams_build --ultra`) → коммит `docs: diagrams for tasks/<task_id>`;
   - дождаться остальных фоновых артефактов и закоммитить их;
   - `ultra.done += artifacts`.

   Перед финальным ревью в рабочем дереве не остаётся ничего незакоммиченного, кроме локальных файлов.

## Шаг 6: Финальное ревью (`review`)

**Финальный фон** стартует вместе с ревью — фоновыми субагентами по файлам команд, через Skill не вызывать: команда заняла бы оркестратор. Стенд им не нужен.
- `demo` = `plan+data` или `plan`: `/simplegen.demo_plan --ultra` → `background.demo_plan`. Нужны кейсы: `background.cases` ещё в `running` → стартовать после него;
- `demo` = `plan+data`: `/simplegen.demo_data_prepare --ultra` → `background.demo_data` — после возврата `demo_plan` и конца финального ревью: демоданные читают готовый код `domain/`. Файл только генерируется: `demo_data_apply` прогон не вызывает. Тестовые записи на стенде демоданными не считаются и не переиспользуются.

Готовое коммитится в ближайшей точке фиксации: `docs: demo plan for tasks/<task_id>` (`_demo_plan.md`). `docs: demo data for tasks/<task_id>` (`_demo_data.json`).

`/simplegen.code_generate --ultra review` — весь дифф `initial_commit_sha..HEAD`, набор «Код»: стыки фаз, которые не видны в ревью одной фазы.
- **Все применимые фокусы**, а не один: `план` — всегда, `скрипты` — есть `.js`, `данные` — есть `data-structure/` или `access-control/`, `интерфейс` — виджеты, формы, списки, меню, локализация.
- **Цикл исправлений обязателен**, до 3 итераций, как в команде. ISSUE, который расходится со спекой или с «Уточнениями к спецификации», исправляется, а не уходит во флаг. Без исправления — только ISSUE, которое прямо закрыто ответом интервью: тогда в журнал «принято на интервью, Q<N>», в MR — флаг со ссылкой на вопрос. Остальное, не исправленное за 3 итерации, — флаги.

Если после ревью `patch` нужен по правилу деплоя: точка фиксации → `patch` по режиму деплоя → коммит write-back.

## Шаг 7: Финал на стенде (`final`)

Основное тестирование — **до `build`**, на `patch`-стенде: дефект здесь чинится обычным `patch`, без пересборки. После `build` — короткая проверка: сборка откатывает пак `patch` и пересоздаёт записи задачи, runtime-данные в её таблицах могут пропасть, поэтому тесты создают свои данные заново.

Перед каждым шагом — `ultra.build_step` и точка фиксации.

1. **`demo` — демо-план и демоданные** — только файлы: дождаться фоновых `demo_plan` и `demo_data` и закоммитить их (Шаг 6). Тесты их не ждут и не читают.
2. **`tests` — все тесты разом** (`deployed_sha = ultra.deployed_head`):
   1. `test-author` (run), порция `final`: все кейсы — под собой, под ролями и «без роли». Данные и пользователей с ролями каждому кейсу создаёт его фикстура (`e2e = product`). При `e2e = own` — данные `test-author` создаёт сам через интерфейс с префиксом `[TEST <task_id>]`, пользователи для ролей — из `options.role_users`, `skip` — кейсы под ролями SKIP. Демоданные не используются.
   2. `test-author` (codify) — для прошедших в браузере IDE; при готовом Playwright `run` уже прогнал кейсы тестами, шаг пропускается.
   3. `test-author` (rerun) — весь Playwright-набор задачи.
3. **`defects`** — дефекты тестов, не более 3 итераций:
   1. `code-author` (fix) → коммит.
   2. Точка фиксации → `patch` по режиму деплоя → коммит write-back.
   3. `test-author` (fix) — только кейсы дефектов, фильтром раннера, а не весь набор.

   `code-author` (fix) получает диагноз `test-author` целиком (DOM, консоль, что вырезано и перерисовано) и правила «Динамический HTML в виджете» `script-rules`; новый механизм — по рабочему аналогу из того же виджета. Весь набор (rerun) — один раз, после того как все дефекты закрыты или исчерпаны итерации. Не закрытые за 3 итерации — флаги; если среди них кейс ключевого критерия приёмки — в заголовке MR `[AC-N не работает]` и первой строкой описания.
4. **`build`.** `/simplegen.product_build --ultra` → коммит `build: <task_id> SOP`: SOP и write-back → `ultra.deployed_head = HEAD`.
5. **`verify` ∥ проверка после сборки** — одним сообщением: `verify` оффлайн и стенда не касается, проверка — только стенд.
   - `/simplegen.product_verify --ultra` — та же проверка, что в пайплайне MR.
     - Расхождение, которое исправляется пересборкой, → действие по таблице команды и повтор, не более 3 попыток. После пересборки — снова проверка после сборки.
     - Требуется ручная правка `.sop` или `product_sync` → стоп. После ручной правки `resume` продолжает с `verify`, не пересобирая.
   - **`after_build` — проверка после сборки:** `test-author` (run), порция `после build`: `rerun` всего набора тестов задачи одной командой, фикстуры заново создают данные. Без Playwright — по одному кейсу «под собой» на каждый FR. Упало → один цикл: `code-author` (fix) → коммит → `patch` → снова п. 4–5. Упало повторно → флаги.
6. **Черновик MR** — после успешного `verify`, фоном: `mr-author` (черновик) по Шагу 8 п. 1 → `background.mr_draft`. Пишет `_local/_mr.md`; итоги тестов к этому моменту уже есть. Файл локальный и не коммитится: описание живёт в самом MR.

**Перед переходом к MR:** коммит, меняющий `<product>/domain/` (кроме write-back `sys_id`) и сделанный позже последнего коммита `build:`, означает, что SOP устарел → снова п. 4–5.

## Шаг 8: Merge request (`mr`)

1. **Описание.** Черновик с Шага 7 есть → `mr-author` (дополнение): итоги тестов, флаги, допущения, этапы и коммиты — по журналу и `_local/test_report.md`, остальное не переписывать. Черновика нет → `mr-author` полностью. Он получает:
   - продукт, `tasks/<task_id>`;
   - ветку и целевую ветку;
   - стенд, сопки, SOP;
   - вывод `verify`;
   - вывод `git log <target>..HEAD --oneline`;
   - `spec_owner`.

   Итоги тестов он берёт из «Итогов» локального `_local/test_report.md` — только цифры, ссылок на локальные файлы в MR нет. Пишет `tasks/<task_id>/_local/_mr.md`, возвращает `MR_TITLE`.
2. В журнале «Статус» — «🔄 создаётся MR». `_local/_mr.md` в ветку не идёт: в репозитории описание MR не нужно, оно живёт в самом MR.
3. **Push и MR** — в bash (на Windows — Git Bash):

   ```bash
   T="$(git rev-parse --git-path ULTRA_TITLE)"   # файл с текстом «Draft: <MR_TITLE>» оркестратор пишет заранее
   git push -u origin <branch>
   glab mr list --source-branch <branch>
   glab mr create --source-branch <branch> --target-branch <target> --title "$(cat "$T")" --description "$(cat <product>/tasks/<task_id>/_local/_mr.md)" --yes
   ```

   - MR для ветки уже есть (повтор после сбоя) → не создавать, взять его URL.
   - Ссылку записать в `ultra.mr_url` сразу после создания.
   - **Нет `glab`, remote — GitLab:**

     ```bash
     git push -u origin <branch> -o merge_request.create -o merge_request.target=<target> -o "merge_request.title=$(cat "$T")"
     ```

     - URL MR — из строк `remote:` вывода push.
     - Push options не принимают многострочный текст: полное описание вывести в чат для вставки в MR.
     - URL нет (ошибка GitLab печатается как `remote:`, при «Everything up-to-date» push options не доходят) → флаг «MR не создан». В чат — описание и ссылка на создание MR: `<web-URL проекта>/-/merge_requests/new?merge_request[source_branch]=<branch>`.
   - **Remote не GitLab** → только `git push -u origin <branch>`; флаг «MR не создан: remote не GitLab», описание — в чат.
   - Отказ push или ошибка `glab` → стоп (`ultra-rules`), `stage` остаётся `mr`.
4. **Финал** — только когда есть URL MR или флаг «MR не создан»:
   - `ultra.status = done`, `ultra.done += mr`;
   - журнал: «Статус» — ✅ готово, «MR» — ссылка или причина;
   - `git push -u origin <branch>`: MR подхватит коммит сам.
5. Уведомить и вывести итог.

## Доработка после MR

Человек после итога просит изменить поведение («сделай по макету», «убери X»):
1. **План и уточнения** — правка `_task_plan.md` (уточнения `У-N`, задачи) и **коммит `plan:`** до кода. План в ветке должен совпадать с кодом.
2. **Код** — `code-author` (fix) → коммит → `patch` → write-back.
3. **Тесты** — кейсы, которые задела правка, обновить и прогнать; затем весь набор.
4. **`build`** → `verify` → push. Описание MR — `mr-author` (дополнение) по новому поведению; без `glab` — текст в чат.
5. В конце `git status`: незакоммиченным остаётся только локальное (`_local/`, `.simplegen/e2e/`).

## Продолжение: `/simplegen.ultra resume`

1. Прочитать активную фичу и `_local/ultra.json` задачи.
   - `status: done` → вывести итог и `mr_url`.
   - Файла нет → «прогон ultra для задачи не запускался на этой машине». Состояние локальное: продолжить прогон с другой машины нельзя.
2. **Повторить проверки Шага 0:**

   - стенд (`whoami`);
